<objective>
Build the two pieces of new logic Phase 5 needs before anything can be rendered: the derived score
ceiling (SCORE-02) and the `getScoreScale()` accessor the scale bar reads (SCORE-03's data source).

Purpose: SCORE-02 exists so the displayed ceiling cannot silently rot when a scored question is
added. `getScoreScale()` exists so `ResultsDisplay` is written once — Phase 5.1 swaps this module's
implementation to a DB-backed read (D-01/D-03) and the component never changes again.
Output: `getQuestionMaxScore`/`getMaxScore` in `scoring.ts`, a new `score-scale.ts` module holding
the provisional constant and its accessor, and unit coverage that proves the ceiling is derived
rather than asserted.

**Scope fence (D-03):** this plan ships a compiled-in constant only. No settings table, no admin
route, no config endpoint, no `scale_version`, no migration — all of that is Phase 5.1.

**D-02 is deliberately out of scope for the whole of Phase 5.** D-02 makes the *clinical bracket*
boundaries editable alongside the visual band stops, which means a `submissions` schema change and a
`scale_version` stamp — a PHI-path change under CLAUDE.md's PR-review rule. Phase 5 therefore leaves
`SCORE_BRACKETS` and `getScoreBracket()` in `scoring.ts` completely untouched: this plan adds functions
beside them and reads neither. Phase 5.1 owns D-02 in full. Nothing in Phase 5 may anticipate it — no
`scale_version` field on `ScoreScale`, no bracket boundary in the scale config, no migration.
</objective>
