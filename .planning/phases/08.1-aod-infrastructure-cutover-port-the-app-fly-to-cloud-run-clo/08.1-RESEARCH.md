## Summary

The port is smaller than it looks because the code was already written env-driven: `GCS_BUCKET_NAME`/`GCS_PROJECT_ID`/`DATABASE_URL` are env vars, and `app/lib/storage/gcs.ts` already falls back to ADC when `GCP_SA_KEY` is absent. The real code changes are: (1) Prisma sessions SQLite -> Postgres, (2) `db.ts` TLS config for the Cloud SQL unix socket, (3) delete the `GCP_SA_KEY` branch, (4) Dockerfile/entrypoint without Litestream/`dbsetup.js`, (5) swap 6 hard-coded `fly.dev` URLs across three deploy systems, (6) adapt the e2e script. Everything else is infra provisioning in `aod-production-510006`, which is currently an empty project: only default APIs are on, Cloud Run/Cloud SQL Admin/Secret Manager/Artifact Registry/Cloud Build/IAM Credentials APIs are NOT enabled, and the only IAM binding is `roles/owner` for `hostmaster@alledrops.com`. [VERIFIED: `gcloud services list` / `gcloud projects get-iam-policy` run 2026-10-05, read-only]

Four findings the planner must not miss, none of which are in the roadmap: (a) `package-lock.json` is gitignored, so `gcloud run deploy --source` (which defaults to gitignore rules) uploads a build context where `npm ci` fails; (b) `.dockerignore` does not exclude `.env`, and `.env` exists locally, so `COPY . .` bakes live credentials into the image; (c) the customer-facing PDF/file download links carry the customer JWT in `?token=`, and Cloud Run request logs record the full request URL; (d) Shopify docs say Dev Dashboard apps cannot be transferred with a store and client-transfer stores cannot have custom/draft apps installed, so "is the quiz app still installed after transfer" is a real risk with a defined fallback (custom-distribution install link), not a formality.

**Primary recommendation:** Keep Prisma and flip its datasource to a separate `shopify_sessions` database on the same Cloud SQL instance (zero new dependencies); connect both pools through the Cloud Run-managed `/cloudsql/` unix socket with passwords from Secret Manager; drop `GCP_SA_KEY` and rely on ADC with `roles/iam.serviceAccountTokenCreator` on the runtime SA for signed URLs; deploy with `gcloud run deploy --source` using a dedicated build SA; keep Fly warm (scaled, not destroyed) until the Shopify transfer is verified.

### Pattern 1 (Q1): Sessions - Prisma stays, datasource becomes Postgres
**Recommendation:** separate DATABASE `shopify_sessions` + role `sessions_app` on the same Cloud SQL instance. Not the PHI database: Prisma needs DDL (`migrate deploy`) and the PHI app role is deliberately SELECT/INSERT(/UPDATE) only (migrations 001/002/004 grants). Sessions hold access tokens and staff names/emails, not patient PHI.
```prisma
// prisma/schema.prisma
datasource db {
  provider = "postgresql"
  url      = env("SESSION_DATABASE_URL")
}
// model Session {...} unchanged (BigInt userId, DateTime? expires map to bigint / timestamp(3) on Postgres)
```
```bash
# regenerate a Postgres baseline; delete prisma/migrations/20240530213853_create_session_table (SQLite DDL: DATETIME)
npx prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script \
  > prisma/migrations/20261005000000_init_postgres/migration.sql
```
Runtime URL (Cloud Run): `postgresql://sessions_app:<PW>@localhost/shopify_sessions?host=/cloudsql/aod-production-510006:us-east1:aod-quiz-db&connection_limit=2` [CITED: Prisma's documented Cloud SQL socket form; ASSUMED here - prove in Wave 1 with `cloud-sql-proxy --unix-socket`]. `connection_limit=2` keeps total connections low (see Pitfall 6).
**Run `prisma migrate deploy` once from the laptop via the proxy (and again only when the schema changes), not at container start.** Today `npm run docker-start` runs `prisma generate && prisma migrate deploy` on every boot, which on Cloud Run means every cold start races for a Postgres advisory lock and needs DDL rights in the runtime role. Move `prisma generate` to the Dockerfile build step; CMD becomes `npm run start`.
`webhooks.app.uninstalled.tsx` and `db.server.ts` need no change. Local dev loses SQLite: document a throwaway Docker Postgres (`SESSION_DATABASE_URL=postgresql://postgres:dev@127.0.0.1:5437/sessions`) in `.env.example`.
**After cutover the session table is empty.** The embedded admin must be opened once in Shopify admin to token-exchange a fresh offline session; until then `unauthenticated.admin(shop)` in `api.quiz.submit.tsx` throws and the code falls back to `SHOPIFY_ADMIN_ACCESS_TOKEN` (see Open Question 1).

### Pattern 2 (Q2): Cloud SQL from Cloud Run
Use Cloud Run's managed connection: `--add-cloudsql-instances aod-production-510006:us-east1:aod-quiz-db` mounts a socket at `/cloudsql/<CONNECTION_NAME>`; the runtime SA needs `roles/cloudsql.client`; the Cloud SQL Admin API must be enabled; gen2 execution environment is the default. [CITED: docs.cloud.google.com/sql/docs/postgres/connect-run] The socket leg is already mTLS-wrapped by the connector, so the app must NOT also negotiate TLS on it. Keep the instance on a public IPv4 with ZERO authorized networks (authorization is IAM via the connector, not IP allow-listing, so the Fly egress allow-list `216.246.40.114/32` simply does not carry over) and `--ssl-mode=ENCRYPTED_ONLY`. If org policy `sql.restrictPublicIp` is enforced, fall back to private IP + Direct VPC egress (Open Question 3).
Create the instance with a per-instance server CA (`GOOGLE_MANAGED_INTERNAL_CA`) - the docs require it for web-app connections. [CITED: same page]
New `db.ts` TLS logic (replaces the unconditional `rejectUnauthorized:false` and its "TODO(prod): pin server CA"):
```ts
// app/lib/db.ts  (sketch)
const u = new URL(databaseUrl);
const viaSocket = (u.searchParams.get("host") ?? "").startsWith("/");   // Cloud Run /cloudsql/...
const mode = u.searchParams.get("sslmode");                              // local proxy => disable
const ssl = viaSocket || mode === "disable" ? false
          : mode === "no-verify" ? { rejectUnauthorized: false }          // legacy dev only
          : { rejectUnauthorized: true };                                 // anything else must verify
_pool = new Pool({ connectionString: databaseUrl, ssl, max: 5, idleTimeoutMillis: 30_000,
                   connectionTimeoutMillis: 5_000, statement_timeout: 10_000 });
```
Gotcha: `pg` merges `connectionString`-parsed options OVER explicit options, so a `sslmode=` in the URL wins over `ssl:`. Unit-test the resulting `pool.options.ssl` for all three URL shapes (Wave 0 test, no DB needed).
**Credentials:** DB password in Secret Manager, whole `DATABASE_URL` as a secret (keeps the existing env contract). Generate passwords alphanumeric-only (`openssl rand -base64 32 | tr -dc A-Za-z0-9`) - the e2e script already documents a `%7D` URL-encoding trap. IAM DB auth is not recommended (needs proxy sidecar).

### Pattern 3 (Q3): GCS with ADC
`gcs.ts` already returns `new Storage({ projectId })` when `GCP_SA_KEY` is unset, and the file's own comment says the Fly "ADC gap" was that Fly has no metadata server - Cloud Run does, so the gap closes by itself. Required code change: DELETE `readServiceAccountCredentials` and the `GCP_SA_KEY` branch (leaving it invites someone to mint a key; org policy blocks it anyway), update `tests/storage-gcs.test.ts` (it tests both branches), and rewrite the header comments that say "Fly".
**Signed URLs need extra IAM** because `getSignedReadUrl` (used by `api.me.assessment.$id.files.$fileId.tsx` and `api.admin.submission.$id.file.$fileId.tsx`) signs with `getSignedUrl`, and compute credentials have no private key; the client falls back to IAM `signBlob`. Therefore: enable `iamcredentials.googleapis.com` and grant the runtime SA `roles/iam.serviceAccountTokenCreator` ON ITSELF (resource-level binding, not project-wide). [CITED: seankhliao.com/blog/12021-08-25-gcp-signed-url-no-key; label-studio GCS guide; ASSUMED that no further flag is needed in @google-cloud/storage 7.21 - prove with the live signed-URL smoke in Q12]
Bucket (names are PHI-free; do not embed anything patient-related):
```bash
gcloud storage buckets create gs://aod-quiz-uploads-prod --project=$P --location=us-east1 \
  --uniform-bucket-level-access --public-access-prevention --soft-delete-duration=0 [DECISION, see below]
gcloud storage buckets update gs://aod-quiz-uploads-prod --lifecycle-file=lifecycle.json   # pending/ age 2 -> Delete (same JSON as docs/gcs-lifecycle-and-retention.md)
gcloud storage buckets add-iam-policy-binding gs://aod-quiz-uploads-prod \
  --member=serviceAccount:quiz-app-runtime@$P.iam.gserviceaccount.com --role=roles/storage.objectAdmin
```
All flags verified present in local gcloud 567.0.0 help. CMEK not needed (Google-managed encryption is within the BAA). Do NOT set a bucket retention policy/lock: it would block the `pending/` lifecycle delete and the promote step's `deleteObject`; the 6-year rule stays an application/policy rule as in the dev bucket. **Decision for Andrew:** new buckets have a default 7-day soft-delete; `--soft-delete-duration=0` removes the 7-day recoverable copy of deleted `pending/` PHI (cleaner for orphan cleanup) but also removes accidental-delete recovery; default 7 days is also inside the BAA. Dev's `objectAdmin` note ("a leaked key could delete permanently-retained objects ... revisit at cutover") largely dissolves because there is no key; keep bucket-level `objectAdmin`, and optionally tighten later with an IAM Condition limiting delete to `pending/`.
CORS is NOT needed (downloads are server-issued 302 navigations, never fetch() from a browser).

### Pattern 4 (Q6): Cloud Run service settings
```bash
gcloud run deploy alle-drops-quiz-app --project=$P --region=us-east1 --source=. \
  --build-service-account=projects/$P/serviceAccounts/quiz-app-build@$P.iam.gserviceaccount.com \

  --set-env-vars=SHOPIFY_APP_URL=https://<RUN_URL>,SCOPES=read_customers\,write_customers,SHOPIFY_API_KEY=1af0c030f06eea4b8b46d3c006f431d3,SHOPIFY_SHOP_DOMAIN=allergist-on-demand.myshopify.com,GCS_BUCKET_NAME=aod-quiz-uploads-prod,GCS_PROJECT_ID=$P \

```
(use `--set-env-vars` with a `^@^` custom delimiter or a `--env-vars-file` for `SCOPES`, which contains a comma). Flags verified in local gcloud help: `--build-service-account`, `--add-cloudsql-instances`, `--cpu-boost`, `--no-invoker-iam-check`, `--set-secrets`, `--min/max-instances`, `--concurrency`, `--ingress`, `--startup-probe`.
Rationale: region `us-east1` = same region as the dev Cloud SQL, Fly `iad` is adjacent, TN/TX patients, and it is a domain-mapping-supported region [CITED]. `min-instances=1` mirrors Fly's `min_machines_running=1`: Node + React Router cold start is multi-second and the quiz is a storefront iframe plus an embedded admin. `memory=2Gi` mirrors the Fly sizing decision in `fly.toml` (streaming HEIC decode + PDF merge; caps 15 MB/file, 50 MB/submission). `concurrency=8` (not the default 80) because a request can hold tens of MB. Request timeout 120 s (default is 300 s, max 3600 s [CITED]). `max-instances=3` is the cost/abuse cap and keeps DB connections bounded. PORT: Cloud Run injects `PORT=8080`; `react-router-serve` reads `process.env.PORT`; remove `PORT=3000`, `EXPOSE 3000`. Health: `/health` already exists and deliberately does not touch the DB (good for a startup probe; it also means it proves nothing about LAUNCH-04).
**What protects a public service (Q6 tail):** `--no-allow-unauthenticated` is impossible, and with the Workspace-created org the domain-restricted-sharing org policy (`iam.allowedPolicyMemberDomains`) commonly blocks granting `roles/run.invoker` to `allUsers`; Google's recommended public path is `--no-invoker-iam-check`, explicitly for projects under that constraint. [CITED: docs.cloud.google.com/run/docs/authenticating/public] Protection is then: per-route app auth (customer JWT with ownership check, Shopify admin session, webhook HMAC), CSP on `/quiz-embed`, `max-instances` cap, and the same unauthenticated `POST /api/quiz/submit` + `/api/quiz/upload` exposure Fly had (no rate limiting exists in the repo - flag, not fix, in this phase). An external ALB + Cloud Armor would add rate limiting and is the same piece of infrastructure needed for the production custom domain, so decide it together (Q8).

### Anti-Patterns to Avoid
- **`GCP_SA_KEY` or any key file on Cloud Run:** org policy blocks it and it defeats the phase goal.
- **Running `prisma migrate deploy` in the container CMD:** DDL rights in runtime role, cold-start lock contention.
- **Pointing Prisma at the PHI database:** it would need DDL rights there.
- **Adding `?sslmode=` to a socket URL:** URL-derived ssl overrides code config and the socket has no TLS endpoint.
- **Deploying with `--source` from a dirty working tree or a feature branch.**

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| DB reachability from Cloud Run | Own TLS/CA pinning, IP allow-lists | `--add-cloudsql-instances` socket | Connector handles mTLS + IAM; removes the "pin server CA" TODO |
| Secret distribution | `.env` baked in image, config in git | Secret Manager + `--set-secrets` | Image must not contain credentials |
| GCS signing credentials | Key JSON, own signer | ADC + IAM signBlob (`serviceAccountTokenCreator` on self) | No key, within org policy |
| Postgres backups/PITR | Cron `pg_dump` | Cloud SQL automated backups + PITR flags | Locked decision; verified flags exist |
| Session persistence | Litestream replacement, volume tricks | Postgres + Prisma | Cloud Run is stateless |
| Build pipeline | Local docker + push scripts | `gcloud run deploy --source` | No registry setup, user creds |
| Public-ness | `allUsers` IAM binding (may be policy-blocked) | `--no-invoker-iam-check` | Documented path under domain-restricted sharing |

## Common Pitfalls

### Pitfall 1: `npm ci` fails in Cloud Build because the lockfile is not uploaded
**What goes wrong:** `package-lock.json` is gitignored (`.gitignore:3`, `git ls-files package-lock.json` -> 0), and gcloud uses gitignore rules when no `.gcloudignore` exists [ASSUMED standard gcloud behavior]. The Dockerfile's `COPY package.json package-lock.json*` then `npm ci` has no lock.
**How to avoid:** add `.gcloudignore` that does not list the lockfile, or commit the lockfile (better reproducibility for a HIPAA app; a repo-policy decision for Andrew). **Warning signs:** `npm ci` "requires an existing package-lock.json".

### Pitfall 2: `.env` baked into the image
**What goes wrong:** `.dockerignore` lists only `.cache`, `build`, `node_modules`; `.env` exists locally; `COPY . .` copies live DB credentials into every image (today's Fly image too).
**How to avoid:** add `.env*`, `.git`, `.shopify`, `.planning`, `scripts/output`, `*.sqlite` to `.dockerignore` and `.gcloudignore`; add a contract test asserting both files contain `.env`. After the first Cloud Build, `gcloud artifacts docker images` + a throwaway `docker run ... ls -a /app | grep .env` must be empty. Treat the existing Fly image as having leaked the dev DB password to Fly's registry; rotate when retiring.

### Pitfall 3: Cloud Run request logs capture `?token=`
See Q9. **Warning signs:** `gcloud logging read 'httpRequest.requestUrl:"token="' --limit=1` returns entries.

### Pitfall 4: HTTP/1 32 MiB limits
Cloud Run HTTP/1 requests are capped at 32 MiB and responses at 32 MiB unless streamed/chunked; HTTP/2 end-to-end has no limit. [CITED: docs.cloud.google.com/run/quotas via search] Uploads are per-file (<=15 MB) so requests are fine; the merged PDF response (up to ~50 MB of embedded files) must be streamed/chunked or it can fail on Cloud Run where Fly did not. Verify with a worst-case 4-photo PDF in Wave 3.

### Pitfall 5: Shared-core tier and tiny `max_connections`
Smallest Cloud SQL tiers allow few connections; pg pool `max:5` x `max-instances 3` + Prisma `connection_limit=2` x 3 = 21. Check `SHOW max_connections;` on the new instance; lower `max-instances` or pool size if needed [ASSUMED tier limits].

### Pitfall 6: Cold-start migration race / DDL at boot
Do not leave `prisma migrate deploy` in `docker-start`.

### Pitfall 7: Prisma + alpine
`node:20-alpine` + `openssl` is what the current Fly image uses and works; keep it. If Prisma engine errors appear on Cloud Run, the fix is `binaryTargets` in the generator, not a base-image change. Node `engines` is `>=20.19 <22`: pin `node:20.19-alpine` or later so `node:20-alpine` drift cannot break it [ASSUMED].

### Pitfall 8: Updating one `shopify.app*.toml` only
Two toml files carry the same `client_id`; `shopify app deploy` without `--config` uses the default one. Deploy and diff both, and confirm in Dev Dashboard that the live version shows the new URLs.

### Pitfall 9: Org-policy surprises mid-build
Run order: read effective policies first (Checkpoint A). If `sql.restrictPublicIp` is on -> private IP path; if `iam.allowedPolicyMemberDomains` is on -> already handled via `--no-invoker-iam-check`; if `gcp.resourceLocations` restricts regions -> us-east1 may not be allowed.

### Pitfall 10: Deploying the wrong tree
`--source` ships the working directory. Deploy from a clean checkout of merged `main` only.

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Credentials baked into image (`.env`) | Information disclosure | ignore files + contract test + image inspection |
| Over-broad runtime SA | Elevation | dedicated SA, bucket-level and secret-level bindings only |
| Public bucket / object | Information disclosure | uniform access + public access prevention; signed URLs 300 s, `attachment` |
| Bearer token in URL query logged | Information disclosure | exclusion filter / header-based follow-up |
| Spoofed XFF in consent record | Repudiation/Tampering | trusted-position parse + test |
| Anonymous endpoint abuse (`/api/quiz/submit`, `/upload`) | DoS | `max-instances`, request size caps, optional LB + Cloud Armor |
| Public Cloud SQL IP | Information disclosure | zero authorized networks, ENCRYPTED_ONLY, connector-only access |
| PHI in resource names/labels/metadata | Information disclosure | [CITED: HIPAA doc] keep names generic (`aod-quiz-uploads-prod`) |
