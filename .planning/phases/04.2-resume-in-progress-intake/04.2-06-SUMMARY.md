## Decisions Made

- Run B's seeded draft restores only Part 7's `had_testing` text answers (not every part), giving
  the "interrupted partway through the now-first Part 7" story — the same fixture shape
  `tests/quiz-resume-restore-dom.test.ts`'s `HAD_TESTING_ANSWERS` already established. This is
  what forces the shared per-part answering loop to genuinely drive Parts 1-6 for Run B rather
  than skip them as already-restored, keeping the loop's behavior meaningfully exercised on both
  runs.
- **Discovered mid-Task-1, load-bearing for the RED proof's validity:** a shared per-part
  answering loop that unconditionally re-types every item to one canonical fixture (the design a
  literal reading of the plan's "shared helper covers only the per-part answering" describes) is,
  by construction, incapable of surfacing a dropped-restored-answer-key bug through final-payload
  equality alone — the loop's job is to drive BOTH runs to the identical target answer set
  regardless of starting state, so it silently retypes whatever a restore bug blanked, before
  that value ever reaches `POST /api/quiz/submit`. Fixed by adding a targeted intermediate
  assertion (`enterResumed()`) that checks the three restored Part 7 text-field DOM values
  immediately after the `Resume` click and before the shared loop runs. This keeps the loop
  itself exactly as simple and shared as the plan specifies, while making RED mutation proof #1
  genuinely non-vacuous rather than accidentally green. See "Patterns Established" above for the
  general lesson.
- The divergent-upload-tokens test diffs by flattening each stripped payload's nested `answers`
  object into the same namespace as its own top-level fields before computing the set difference.
  A flat top-level-only diff would report `"answers"` as the one differing key (since it is the
  sole top-level field containing the divergent `testing_files` array) rather than
  `"testing_files"` by name, which the plan's acceptance criteria explicitly requires. Verified
  safe against key collisions: no real `SubmitPayload` top-level field name (`state`, `name`,
  `dob`, `email`, `phone`, `symptom_profile_id`, `quiz_score`, `score_bracket`, `quiz_date`,
  `answers`, `completion_time`, `consent_version`) collides with any real quiz answer ID.
