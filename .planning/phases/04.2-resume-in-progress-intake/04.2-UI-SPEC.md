# Phase 04.2 — UI Design Contract: Resume In-Progress Intake

> Visual and interaction contract for ROADMAP success criteria 1–5 (04.2-CONTEXT.md D-01…D-11).
> Generated by gsd-ui-researcher, to be verified by gsd-ui-checker. There is no RESEARCH.md for
> this phase — every token, class, and pattern below is derived directly from
> `app/styles/quiz.module.css` and the five component files enumerated in `<files_to_read>`
> (`QuizContainer.tsx`, `StateGate.tsx`, `QuizProgress.tsx`, `QuizNavigation.tsx`,
> `QuizPartRenderer.tsx`), not invented. Design-system posture is unchanged from Phase 3/4: no
> Tailwind, no shadcn, no component library, no design-token file — hand-written React + CSS
> Modules. This phase is small visually (one new screen, one new low-emphasis control, two copy
> variants, one restoration notice) but carries the app's **first true destructive, confirmation-
> gated UI action** (clearing a draft), so the confirmation pattern gets real weight below.

## Color

Zero new colors. Every value is a Shopify theme CSS custom property or one of the three fixed
semantic hex values already declared once (`quiz.module.css:31-33`) — unchanged from Phase 3/4.

**What this phase changes:** `--quiz-color-error` moves from "validation feedback on the
patient's own in-progress input" (Phase 4's framing) to, for the first time, **a real destructive
confirmation action** — clearing a saved or in-progress draft is data loss the patient cannot
undo. Flagging this explicitly so the checker's Color dimension treats it as a deliberate new use,
not scope creep.

| Role | Value | Usage in this phase |
|------|-------|----------------------|
| Dominant (60%) | `rgb(var(--color-background, 255, 255, 255))` | Resume-offer card background, confirm-panel background — unchanged, same as every other screen |
| Secondary (30%) | `rgba(var(--color-foreground, 32, 34, 35), 0.03–0.15)` | Resume-offer card border, confirm-panel border, the persistent "Start over" control's resting text color (`rgba(var(--color-foreground, 32, 34, 35), 0.6)` — a low-emphasis utility link, not a primary action) |
| Accent (10%) | `rgb(var(--color-button, 0, 123, 255))` | **Reserved for (unchanged list, one addition):** the "Resume" button, styled identically to every other primary forward-navigation action (`.quizNavigation__buttonNext`) — it joins existing reserved-for item "Next / Continue / Submit navigation controls," not a new bucket |
| Destructive | `var(--quiz-color-error, #F44336)` | **New real use, first in the app:** the "Yes, start over" confirm button (outlined, not filled — see Component Inventory §3) on both the resume-offer's inline confirm panel and the persistent mid-flow control's inline confirm panel |

**Accent reserved for, explicit list (Phase 4's seven items, "Resume" folded into item 3, no new
item added):**
1. Selected checkbox/radio option border + background tint
2. Input/select focus ring
3. Next / Continue / Submit / dropzone-focus / results-CTA / **Resume** — all primary
   forward-navigation controls, one visual language
4. The progress bar fill
5. The info-block left border, its icon, and existing `strong`/monospace accents
6. The file-upload dropzone's "+" icon and its focus/hover border

**Explicitly NOT accent:** the persistent "Start over" control (neutral/secondary, not accent —

### Base-copy provenance (not verbatim-locked — Claude's Discretion per CONTEXT.md)

The resume-offer heading/subtitle are the same sentence CONTEXT.md D-06 quotes as its own
example (*"You have an unfinished assessment from earlier. Resume, or start over?"*), split at the
period into heading + subtitle to fit the existing `.questionCategory__title` /
`.questionCard__subtitle` two-line pattern `StateGate.tsx` already uses. CONTEXT.md's Claude's
Discretion section explicitly grants "exact neutral copy wording... within D-06's no-identity
constraint," so this is **recommended, not locked verbatim** — unlike Phase 4's "Schedule Allergy
Testing," which CONTEXT.md marked LOCKED. A planner/executor may adjust wording, but any
replacement must independently satisfy: (a) no name, no DOB, no email, no phone, no initials, no
avatar; (b) no elapsed-time display (Andrew explicitly chose bare-neutral over the timestamped
variant); (c) parallel one/two-word button labels ("Resume" / "Start over"), which the primary
CTA and D-08's own locked term ("start over") already fix regardless of heading wording.

### Locked / verbatim terminology (do not paraphrase)

- **"Start over"** — the exact control name from ROADMAP criterion 3 and CONTEXT.md D-08. Do not
  substitute "Reset," "Clear," "Restart," or "Start fresh" — this is the one piece of copy in this
  phase that is a locked term, not a proposal, and it must read identically on both the
  resume-offer button and the persistent in-flow control so a patient recognizes it as the same
  action in both places.

### Primary CTA wording — "Resume" kept as a single word (reviewed, no change)

The primary CTA on the resume-offer screen is **"Resume"** — a single word, no trailing noun. This
was flagged as a non-blocking recommendation during checker review and is kept as-is deliberately:
it is parallel with the locked "Start over" term (both are short, verb-first, two-word-or-fewer
labels sized for the same vertical button stack — see Component Inventory §1's diagram), and
"Resume [what]" has no natural short noun that isn't redundant with the heading directly above it
("You have an unfinished assessment from earlier."). No further change needed; do not re-flag this
on a future checker pass.

### Dismiss-action wording — why "Keep my answers" / "Keep my progress," not "Cancel"

Both confirm-panel dismiss labels name what stays intact rather than using a generic dismissal
verb, and each is worded to match its own confirm body copy exactly: "Keep my **answers**" pairs
with the resume-offer variant's "lose your saved **answers**," and "Keep my **progress**" pairs
with the in-flow variant's "lose your **progress**." "Cancel" is deliberately not used here —
inside a panel headed "Start over and lose your saved answers?", "Cancel" is genuinely ambiguous
(it can read as "cancel the assessment" rather than "cancel the start-over"), and it is a generic
CTA label this phase's copy discipline avoids. Both labels stay parallel in visual and semantic
weight with "Yes, start over" (one clause naming the safe outcome, one clause naming the
destructive one) and both reuse the neutral `.quizNavigation__buttonPrev` treatment unchanged —
this is a copy-only fix, not a new visual component.

### D-09/D-11 dropzone copy — why this exact wording, not a generic empty state

Constraint 5 requires the dropzone copy to explain the file specifically was not kept, without
implying the clinic lost it. **"For your security, files aren't kept between visits."** frames the
absence as a deliberate, patient-protective design choice (true — D-09/D-11 chose this
specifically to avoid a dead GCS reference, and not persisting file bytes to `localStorage` is
also a smaller PHI-at-rest footprint on the shared device). It does **not** say "we couldn't
restore your file," "your upload failed," "there was an error," or anything implying loss or a
bug. This copy renders in place of, never alongside, the default `"No files added yet."` string —
mutually exclusive, selected by a `resumedSession` boolean (or equivalent) passed down to
`QuizPartRenderer`, used only to choose which literal renders inside the existing
`.fileUpload__empty` class. **Zero new CSS** — same class, same visual weight as the default
empty state, so this reads as expected behavior, not a warning (it must never use
`--quiz-color-error` or the `⚠` glyph convention Phase 4 established for validation errors — this
is not a validation error, it is expected, designed behavior).

### Restoration notice — why generic, and why it does not violate D-06

"Your previous answers have been restored." carries **zero** identity — no name, no answer
content, no count of questions restored, no elapsed time. Showing it does not weaken D-06 because,
unlike the resume-offer screen (which must be safe for **anyone** who opens the browser, proven or
not), this notice only ever renders **after** the patient has already clicked "Resume" — the same
accepted trust boundary the whole browser-local design already rests on (CONTEXT.md and ROADMAP
both name the shared-device risk as an accepted, mitigated trade-off, not something every
downstream screen must re-litigate). Its purpose is purely to prevent "wait, did I already answer
this?" confusion from pre-filled fields, not to re-establish identity.

## Flow Contract — where the resume offer sits, and the progress-counter decision (constraint 3)

**New `FlowStep` value: `"resume_offer"`.** Rendered conditionally, before `"state_gate"`, only
when a feature-detect (D-01) finds writable storage AND a stored draft exists AND that draft has
not expired (D-05, 24h) AND that draft actually contains at least one persisted answer (D-07 — an
untouched page load can never produce a draft, so this condition is never independently false in a
way that needs its own UI state; see Absent State).

```
[resume_offer]  →  Resume  →  restored FlowStep (always quiz_parts or consent — see below)
      │
      └────────────→  Start over (confirmed)  →  state_gate   (draft cleared, same as no draft existed)

(no valid draft, or storage unavailable)  →  state_gate   (today's exact behavior, unchanged)
```

**Why the restored step is always `quiz_parts` or `consent`, never `patient_info` or earlier:**
D-07 writes nothing until the first real answer to a quiz *question*, and quiz questions only
exist inside `quiz_parts`. A patient who closed the tab during `state_gate` or `patient_info`
leaves no draft at all — `resume_offer` is architecturally unreachable for those cases, not merely
unlikely. State this to the planner as a closed case, not an open one requiring its own resume
target.

**Progress counter decision (constraint 3): `resume_offer` renders with NO `QuizProgress` bar at
all — it is outside the counter entirely, exactly like `ineligible`, `submitting`, `error`, and
`results` already are today** (`QuizContainer.tsx`'s `progressInfo` ternary already returns `null`
for any `step` value not explicitly mapped to a `FlowProgressStep`; `resume_offer` simply joins
that existing "unmapped, no bar" set — **zero change** to `quizFlowProgress`, `FlowProgressStep`,
or the `NON_PART_STEPS = 3` arithmetic in `app/lib/quiz/schema.ts`).

**Why this is the safe choice, not a placeholder decision:** Phase 4.1 just closed UAT defect #6,
where the counter's noun and denominator silently changed mid-flow and passed 550 green tests
before a human caught it. `quizFlowProgress`'s total is `totalParts + 3` (state_gate, patient_info,
consent) — a fixed, load-bearing constant multiple other parts of the app already depend on
(`at(total)` for consent, `at(2)` for patient_info). Inserting `resume_offer` as step 0 or step 1
of that sequence would require renumbering every subsequent step, is untestable as a "step count"
concept (a screen a patient may never see, shown at most once, is not a fixed position in a
ten-minute questionnaire), and reopens exactly the class of defect Phase 4.1 just closed. Treating
it as a pre-flow interstitial — visually and structurally identical to how `ineligible` already
works today (a screen that can end the session before the counter starts meaning anything) — is
the only choice consistent with the existing, already-correct pattern.

**Restoration lands the patient directly on the restored step with the normal renderer for that
step — no new "review" screen.** This is the direct implementation of D-10 (constraint 7):
resuming must not introduce any surface that could let a patient silently edit a clinical answer
outside the normal, already-reviewed editing flow. `QuizPartRenderer` and `ConsentStep` render
exactly as they do for a same-session patient; the only observable differences are (a) the answers
are pre-filled, (b) the one-time restoration notice (see Copywriting Contract), and (c) for a
restored `had_testing` session, the file dropzone is empty with the D-09/D-11 copy above. **Do not
add a "review your answers before continuing" step.** This is an explicit non-goal, not an
oversight — flagged here so a planner does not read "resume" as implying a review surface.

## Absent State (D-01, constraint 6)

**There is no component to design here — that is the point.** When storage is unwritable, or no
valid non-expired non-empty draft exists, `resume_offer` is simply never entered as a `FlowStep`.
The app renders `state_gate` first, exactly as it does today with zero code from this phase. No
error text, no warning banner, no degraded-mode notice, no "your browser doesn't support saving
your progress" message — any of those would be **more** patient-visible surface area than today's
behavior, which is the one thing D-01 explicitly forbids. A storage-unavailable patient's
experience of this phase is: nothing changed. Confirm in code review that the feature-detect
failure path and the "no draft found" path are visually indistinguishable (both simply do not
render `resume_offer`) — they should not even be reachable as two different code branches that
happen to look the same; ideally they are the same branch (see CONTEXT.md Claude's Discretion:
"where the feature-detect lives" is implementation territory, but the UI contract is identical
regardless of which of the two reasons applies).

## Component Inventory — new / modified for Phase 04.2

### 1. Resume-offer screen — reuses `.questionCard` / `.questionCard__optionsVertical` verbatim

**No new wrapper class.** Structurally identical to `StateGate.tsx`'s existing pattern — same
`.questionCard` outer card, same `.questionCategory__title` heading, same
`.questionCard__subtitle` body line, same `.questionCard__optionsVertical` vertical button stack.
This is the strongest "reuse before invention" case in the phase: the resume offer and the state
gate are both "one decision, two mutually-exclusive vertical buttons, no third partial option,"
the exact shape `StateGate.tsx` already renders.

```
┌─────────────────────────────────────────┐
│  You have an unfinished assessment       │  ← .questionCategory__title
│  from earlier.                           │
│                                           │
│  Resume where you left off, or           │  ← .questionCard__subtitle
│  start over?                             │
│                                           │
│  [        Resume        ]                │  ← .quizNavigation__buttonNext (accent, primary)
│  [      Start over       ]                │  ← .quizNavigation__buttonPrev (neutral, secondary)
└─────────────────────────────────────────┘
```

**Which action is primary, and why (constraint: justify):** **Resume is primary** (accent-filled,
`.quizNavigation__buttonNext` treatment), **Start over is secondary** (neutral outline,
`.quizNavigation__buttonPrev` treatment) — the same visual hierarchy `StateGate.tsx` already uses
for its "Yes" vs. "No — I live in another state" pair. Justification: the entire reason this
phase exists is that the large majority of patients who see this screen intend to finish an
assessment they already started — Phase 04.1's own rationale ("abandonment costs seconds, not ten
minutes") is a bet that most abandonment is circumstantial (closed the tab, phone rang, browser
crashed), not a deliberate decision to quit. Defaulting visual weight toward the completion path
matches that bet and reduces friction for the common case. Making "Start over" equally or more
prominent would work against the phase's own stated goal of reducing lost intakes.

**No progress bar** — see Flow Contract above.

**No third state on this screen.** There is no "loading" or "checking for a draft" visible state —
by the time `resume_offer` is chosen as the active `FlowStep`, the draft has already been read
synchronously (or the step would never have been entered at all; see Absent State). Do not add a
spinner or skeleton here.

### 2. Persistent in-flow "Start over" control (D-08)

New class family: `.quizStartOverRow` (wrapper) and `.quizStartOver` (the control itself).

- **Placement:** a new thin row directly below `.quizProgress` (the "Step N of M" bar),
  right-aligned, `justify-content: flex-end`, `margin-top: var(--quiz-spacing-xs)`. Deliberately
  **not** placed in the bottom navigation row alongside Previous/Next/Continue/Submit — proximity
  to those high-frequency primary controls is exactly the mis-tap risk constraint 4 names, so this
  control lives in its own row, visually separated.
- **Visibility:** renders only when `step` is `"quiz_parts"` or `"consent"`. Hidden on
  `"state_gate"`, `"patient_info"`, `"resume_offer"`, `"ineligible"`, `"submitting"`, `"results"`,
  `"error"` — this range is not arbitrary, it exactly traces D-07's "first write" boundary (see
  Flow Contract): the control is visible precisely when a draft could exist to clear, and hidden
  precisely when one cannot yet exist. A patient on `patient_info` who has typed nothing into any
  quiz question has nothing "start over" could clear, and showing the control there would raise a
  "start over what?" question with no good answer.
- **Visual treatment:** low-emphasis text button, NOT accent-colored (see Color). Caption
  typography role, `color: rgba(var(--color-foreground, 32, 34, 35), 0.6)` at rest,
  `text-decoration: underline` plus full-opacity foreground color on `:hover`/`:focus-visible`,
  small restart-arrow inline SVG (16×16, `aria-hidden="true"`) at `--quiz-spacing-xs` gap before
  the text. Minimum 44×44px tap target via padding (existing accessibility floor), even though the
  visible glyph+text is small — this is Phase 4's `.fileUpload__remove` precedent (small visible
  target, generous padding) reapplied.
- **Behavior on click:** does not navigate or clear anything immediately — opens the inline confirm
  panel (Component Inventory §3, in-flow variant), directly below this row.

### 3. Inline "Start over" confirm panel — shared pattern, two copy variants, first destructive action in the app

**No modal, no dialog, no overlay, no focus trap.** This codebase has zero existing
modal/dialog component (confirmed by grep across `quiz.module.css` and the component files — the
one existing confirmation, `Test Mode`'s `confirm()` call in `QuizContainer.tsx`, is a native
browser dialog used only for an internal QA shortcut, not a patient-facing pattern, and is not
reused here). Building a real modal (focus trap, backdrop, `Escape` handling, `aria-modal`) is
disproportionate engineering for this feature. **Instead: an inline two-step disclosure**, reusing
existing card/button classes, that expands in place where the triggering control lives.

**Resume-offer variant:** clicking "Start over" replaces the two-button row (§1's diagram) in
place — same card, same position, no layout jump elsewhere on the page — with:

```
┌─────────────────────────────────────────┐
│  You have an unfinished assessment       │  ← heading/subtitle UNCHANGED, stay visible
│  from earlier.                           │
│  Resume where you left off, or           │
│  start over?                             │
│                                           │
│  Start over and lose your saved          │  ← confirm heading, .questionCategory__title
│  answers?                                │     (smaller visual weight acceptable — see note)
│  This clears everything you entered      │  ← confirm body, .questionCard__subtitle
│  earlier. This can't be undone.          │
│                                           │
│  [    Keep my answers     ]              │  ← .quizNavigation__buttonPrev (neutral) — FIRST
│  [     Yes, start over     ]             │  ← NEW: outlined, --quiz-color-error — SECOND
└─────────────────────────────────────────┘
```

**In-flow variant:** clicking the persistent control (§2) expands an inline panel directly below
`.quizStartOverRow`, same internal structure (confirm heading, confirm body, a "Keep my progress"
dismiss action, Yes-start-over), sized to the compact utility-row context rather than a full card —
`.questionCard`-style padding and border, but width-constrained to the row rather than the full
question-card width. Quiz content below it is unaffected (pushed down, not overlaid, not
obscured).

**Button order and why the dismiss action comes first:** the dismiss action ("Keep my answers" on
the resume-offer variant, "Keep my progress" on the in-flow variant) renders before
`Yes, start over` in both variants, and **receives programmatic focus when the panel opens** (not
the destructive button). This is the direct mitigation for constraint 4's named failure mode —
"losing a half-finished ten-minute clinical questionnaire by mis-tapping is a real failure mode."
Placing and focusing the safe option first means a patient who reflexively presses Enter/Space
again after tapping "Start over" lands back on the dismiss action, not on the irreversible action.
This mirrors the OS-level convention (e.g., "Move to Trash" dialogs default focus to Cancel, not
Delete).

**New button treatment: `.quizStartOver__confirmButton`** (or equivalent name at implementation
time) — same box shape, padding, radius, and 44px minimum height as `.quizNavigation__buttonPrev`,
but `border-color` and `color` set to `var(--quiz-color-error)`, background transparent (NOT a
filled red button — filled would visually equate "clear my draft" with a system-critical error
state, which overstates the severity of a patient-initiated, fully-intentional action). The
dismiss action ("Keep my answers" / "Keep my progress") is a plain, unmodified reuse of
`.quizNavigation__buttonPrev` — copy only differs per variant, no new visual treatment.

**Accessibility for the panel:**
- Do **not** use `role="dialog"` or `role="alertdialog"` — those roles carry an implicit contract
  (focus trap, `Escape`-to-close, `aria-modal="true"`) this inline, non-overlay pattern does not
  fulfill; applying the role without the behavior is a worse violation than omitting it.
- Wrap the panel in `aria-live="polite"` so its appearance and heading text are announced,
  consistent with the `aria-live="polite"` pattern `QuizPartRenderer.tsx`'s file list already
  establishes in this codebase.
- Programmatic focus moves to the dismiss button ("Keep my answers" / "Keep my progress") on open
  (see above) — this satisfies screen-reader announcement without a redundant separate
  live-region-only signal, and it satisfies keyboard operability (`Tab` reaches both buttons in
  visual order; `Enter`/`Space` activates either).
- The dismiss action collapses the panel back to its trigger's resting state (the two-button row
  for the resume-offer variant, the row-only state for the in-flow variant) with no side effects —
  the stored draft and in-memory state are both untouched.
- `Yes, start over` clears the stored draft and resets in-memory quiz state, then routes to
  `"state_gate"` in both variants — the same landing screen a patient with no draft sees today.
  This is a user-visible outcome commitment (both trigger points must land the patient in the same
  place), not implementation detail.

### 4. Resumed-session file dropzone empty state (D-09/D-11)

**Zero new CSS.** `QuizPartRenderer.tsx`'s existing `entries.length === 0 ? <p
className={styles.fileUpload__empty}>...</p>` branch gains a second literal, selected by a boolean
(name TBD at implementation — e.g. `resumedSession`) passed down from `QuizContainer` through
`QuizPartRenderer`'s existing prop chain. See Copywriting Contract for the exact string and why it
is copied verbatim, not paraphrased at implementation time. The flag needs no reset logic once set
true for a resumed session — once the patient adds any file, `entries.length > 0` and neither empty
string renders, so the distinction only ever matters while the dropzone is genuinely empty.

**This is the only visual change to the file-upload widget in this phase.** Every other Phase 4
`.fileUpload*` rule (dropzone sizing, chip styling, status icons, error copy, retry action) is
unchanged — D-09 makes the upload *requirement* re-apply on resume (a behavioral/flow fact, not a
visual one); the required-but-empty error copy (`"⚠ Add at least one file to continue."`) still
fires exactly as Phase 4 specified if the patient tries to proceed without re-adding a file.

### 5. Post-resume restoration notice (D-06-safe restoration feedback)

**Reuses `InfoBlockCard`'s exact visual family** (`.infoBlockCard`, `role="note"`, the existing
info-icon SVG, `.infoBlockCard__paragraph`) — **zero new CSS.** Rendered once, as the first item
inside `.quizContainer__questions`, immediately above the restored part's first question card, only
on the first render of the step the patient is restored into (`quiz_parts` or `consent`). No
heading, one paragraph (see Copywriting Contract), no bullets. Disappears on the next
`Next`/`Previous`/`Continue` navigation — it is a one-time orientation cue, not a persistent banner,
so it does not accumulate visual clutter through the rest of the session.

**Why `InfoBlockCard`, not a new toast/snackbar component:** this codebase has no toast/snackbar
pattern (confirmed absent from `quiz.module.css`), and `InfoBlockCard` already carries the exact
semantics needed — supplementary, non-interactive, ARIA `role="note"` information that is
structurally distinct from a question card (Phase 3's session-32 defect prevention — a patient must
never mistake this notice for something requiring an answer). Building a new transient-notice
component for one string used once per session would be invention where reuse already fits.

### 6. What this phase does NOT add (explicit non-goals, to prevent scope creep)

- No "review your answers" screen (D-10 / constraint 7 — see Flow Contract).
- No elapsed-time display anywhere in the resume-offer copy (D-06 — Andrew chose bare-neutral).
- No name/DOB/email/phone/initials/avatar anywhere on the resume-offer screen (D-06).
- No staged-file existence check or "your file may have expired" messaging (D-11 — D-09 makes this
  dead code by construction; always re-requiring the upload closes the hazard without probing GCS).
- No modal/dialog component, no focus-trap library, no third-party confirmation-UI dependency
  (§3 above).
- No visible countdown or "your session expires in..." messaging tied to the 24-hour clock (D-05) —
  expiry is silent and, per the Absent State section, indistinguishable from "no draft."
