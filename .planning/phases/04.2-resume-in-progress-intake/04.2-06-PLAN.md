Build one shared fixture — a complete answer map covering every required question in every part of
the real `QUIZ_PARTS`, using the `had_testing` branch so Part 7's mandatory upload is exercised.

Stub `fetch` once for both runs with a single handler that returns `{ token: "tok_parity_fixture" }`
for the upload endpoint and `{ success: true }` for the submit endpoint, and records every submit
body. Returning the SAME token in both runs is deliberate and must be commented: the staging token is
a server-issued opaque value, so holding the server constant is what isolates the variable under
test, which is the resume path. It is NOT a fourth exclusion — `RESUME_PARITY_EXCLUDED_FIELDS` stays
at exactly three, and a test in `payload.test.ts` already enforces that.

Structure the two runs so they share the per-part answering loop but genuinely differ at the entry:

  Run A (one sitting) — empty `localStorage`. Render `QuizContainer`, click through the state gate,
  type the patient info, then drive every part with the shared answering loop (including the real
  file upload against the stubbed `fetch`), reach consent, check the box, submit. Capture payload A
  from the recorded submit body.

  Run B (resumed) — `cleanup()`, clear `localStorage`, then seed a draft representing the same
  patient interrupted partway: same `patientState`, same `patientInfo`, same `symptomProfileId`, and
  the same answers for the parts already completed (with no `testing_files` key, since that is never
  persisted). Mount a FRESH `QuizContainer`, assert the resume offer is showing, click `Resume`, then
  drive the remaining parts with the SAME shared answering loop — including re-uploading the file on
  Part 7, which the D-09 landing rule will have put the patient back on. Reach consent, check the
  box, submit. Capture payload B.

Anti-vacuity requirement, stated in a comment: the shared helper must cover only the per-part
answering, never the entry. If both runs entered through the same code path the test would prove
nothing. Assert explicitly inside run B that the resume-offer heading was present before `Resume` was
clicked, so a regression that silently skipped the offer would fail here rather than pass quietly.

Assertions:
  - Delete every key in the imported `RESUME_PARITY_EXCLUDED_FIELDS` from copies of A and B, then
    `expect(strippedB).toEqual(strippedA)`. Import the constant; do not re-declare it locally and do
    not use `expect.any(...)` in place of the deletion.
  - `expect(B.quiz_score).toBe(A.quiz_score)` and `expect(B.score_bracket).toBe(A.score_bracket)` as
    separate strict assertions — these are the two clinical values criterion 5 names.
  - `expect(B.answers).toEqual(A.answers)`, asserted separately as well, since `answers` is the field
    a restore bug would most plausibly corrupt.
  - Non-vacuity: assert the stripped payload has at least 9 keys and that `A.answers` has at least 10
    entries, so a construction where both payloads were empty could not pass.
  - RESUME-03 tie-in: after each successful submit, assert
    `window.localStorage.getItem(DRAFT_STORAGE_KEY)` is `null`.
  - Each excluded field is present and well-formed in both payloads (a number for `completion_time`,
    a parseable ISO string for `quiz_date`, an `AOD_`-prefixed string for `symptom_profile_id`), so
    the exclusion never hides a missing field.

**Second test in the same file — divergent upload tokens.** The parity test above holds the mocked
upload token constant across both runs, which correctly isolates the resume path as the only
variable. But in production the token is `crypto.randomUUID()` (`app/routes/api.quiz.upload.tsx:124`)
and the two runs' tokens WILL differ. The constant-token choice is reasoning, and this project's rule
is that reasoning gets proven, not asserted. Add `it("tolerates divergent upload tokens", ...)`:

  - Same two-run structure, but the stubbed upload endpoint returns `{ token: "tok_run_a" }` during
    run A and `{ token: "tok_run_b" }` during run B (switch on a counter in the handler, not on any
    property of the request — the client must not be able to influence which token it gets).
  - Strip `RESUME_PARITY_EXCLUDED_FIELDS` from both, then assert that
    **`testing_files` is the ONLY remaining key whose value differs**. Compute this as a set
    difference over the keys of the two stripped payloads rather than by deleting `testing_files` and
    re-comparing, so that a second divergent field would surface by name in the failure output
    instead of being silently swallowed.
  - Assert `B.quiz_score === A.quiz_score` and `B.score_bracket === A.score_bracket` still hold —
    a differing token must not perturb either clinical value.
  - Comment that this test exists to keep `RESUME_PARITY_EXCLUDED_FIELDS` at exactly three: if a
    future change makes some other field token-derived, this test fails and forces the conversation,
    rather than someone widening the exclusion list to make a red test green.

Before committing, prove the test is not vacuous. Run each of these two mutations separately, confirm
