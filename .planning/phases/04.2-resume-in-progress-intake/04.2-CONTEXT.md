# Phase 04.2: Resume In-Progress Intake - Context

**Gathered:** 2026-08-10
**Status:** Ready for planning

<domain>
## Phase Boundary

A patient who closes the tab mid-intake and returns to the quiz **in the same browser** is offered
their prior answers and can either resume or start fresh.

**Browser-local only.** No server-side draft store, no draft PHI table, no email provider, no magic
link, no cross-device resume. The server draft + emailed magic link variant was scoped and
deliberately dropped (~1+ week, two new BAA surfaces) — see STATE.md `Roadmap Evolution`. This phase
does not reopen that.

Delivers ROADMAP success criteria **1–5** for Phase 04.2 and nothing else.

**Correction, 2026-08-10:** an earlier draft of this file said "criteria 1–4." The ROADMAP defines
**five**. Criterion 5 was missing and is the most testable requirement in the phase:

> **Criterion 5:** *"The score and submitted payload are identical whether an intake was completed in
> one sitting or resumed — resume changes persistence only, never clinical data."*

- **D-10: Resume must be clinically inert.** A resumed intake and a single-sitting intake with the
  same answers must produce a **byte-identical submit payload** and an identical score. Persistence
  is the only thing this phase changes. The planner must treat this as a testable invariant, not
  prose — the natural shape is a test that drives the same answers through both paths and asserts
  deep equality on the payload handed to `POST /api/quiz/submit`, plus equality of `quiz_score` and
  `score_bracket`.
- Fields that legitimately differ (`completion_time`, and any wall-clock timestamp) must be
  explicitly excluded from that comparison **and named in the test**, so the exclusion is a
  deliberate, reviewable list rather than a loose matcher.

</domain>

<decisions>
## Implementation Decisions

### Storage substrate and browser support

- **D-01: Degrade silently when storage is unavailable.** Feature-detect writable local storage on
  load. If it is not writable, **never show the resume offer and never promise persistence** — the
  patient gets today's exact behavior. No error, no warning, no permission prompt.

- **D-02: Do NOT use the Storage Access API, and do NOT move the quiz to a first-party surface in
  this phase.** Both were considered and rejected here. The Storage Access API would put a browser
  permission dialog on a clinical intake page before the patient has typed anything. Moving the quiz
  same-origin via a Shopify App Proxy is an architecture change beyond this phase's boundary — see
  `<deferred>`.

- **D-03 (OPEN — measurement, not a preference):** Whether third-party storage actually survives in
  the iframe is **unresolved and must be measured by the researcher, not assumed.** The quiz runs in
  a cross-origin iframe (`extensions/quiz-block/blocks/symptom-quiz.liquid:3`, with
  `frame-ancestors *` at `app/routes/quiz-embed.tsx:141`), so any draft lands in **third-party /
  partitioned storage**, not ordinary first-party storage. Chrome and Firefox partition it; Safari's
  ITP may cap or block it outright. **The ROADMAP's "browser-local localStorage only" decision was
  made without this constraint recorded next to it.** D-01 is the policy that makes the phase safe
  regardless of how the measurement lands, but the researcher must establish the real per-browser
  behavior — measured on the deployed storefront page, not inferred from documentation — before
  planning locks an approach. If it turns out storage is unavailable in a *majority* of real patient
  browsers, escalate to Andrew before planning rather than shipping a feature most patients never
  see.

### What the draft holds

- **D-04: Persist the full intake state, including identity PHI** — name, DOB, email, phone, plus
  all quiz answers and flow position. Chosen over the narrower "symptom answers only" option.

  **Consequence, recorded deliberately:** this is the combination with the largest shared-device
  exposure — identity PHI at rest on the device for 24 hours (D-05). Claude recommended persisting
  answers only; Andrew chose full persistence with that trade-off stated. **This is an informed
  choice, not drift.** D-06 and D-07 are the mitigations that make it defensible and are therefore
  not optional.

- **D-05: 24-hour expiry.** A draft older than 24 hours is treated as absent and cleared. Covers the
  realistic interrupted-then-returned-that-evening case without leaving clinical data on a shared
  machine for a week.

### Resume UX and safety

- **D-06: The resume offer must reveal NO identity.** Copy is neutral — *"You have an unfinished
  assessment from earlier. Resume, or start over?"* — with no name, no DOB, no email. Stored
  identity is written back into the form **only after** the patient chooses Resume. This is the
  direct mitigation for D-04: whoever opens that laptop next sees the offer screen before proving
  they are the patient, and the offer screen must leak nothing. **A personalized greeting
  ("Welcome back, [name]") was explicitly considered and rejected.**

- **D-07: First write happens on the first real answer to a quiz question.** The state gate and
  patient-info typing leave nothing on disk. Identity PHI is only persisted once the patient has
  answered at least one clinical question — so a curious or accidental page load never persists a
  name. This is the operative reading of ROADMAP criterion 2 ("an untouched page load leaves no
  trace").

- **D-08: Clear on successful submission, and an explicit "start over" control clears on demand.**
  Carried forward directly from ROADMAP criteria 3 — already decided, not re-opened here.

### The upload branch (interaction with Phase 04.1)

- **D-09: Restore all answers; always re-require the file upload.** Phase 04.1 moved
  `PART7_ALLERGY_TESTING` to the front, so the required upload is now the third screen. Uploaded
  file bytes and the staged GCS token are **not** persisted. On resume, every text answer comes back
  — including testing year, location, and allergens — and the dropzone returns **empty** with clear
  copy that the file needs re-attaching.

  **The 04.1 wall must survive resume:** a resumed patient on the `had_testing` branch still cannot
  continue without an upload. Do not let restored state satisfy the file-required predicate.

- **D-11: The dead-staged-file hazard, and why D-09 already closes it.** The ROADMAP raises this as
  a concrete plan requirement: after 04.1 the upload comes first, so a resuming patient may have
  already staged a file server-side under `pending/`, which the GCS lifecycle rule deletes at
  `PENDING_OLM_AGE_DAYS = 2`. The ROADMAP's stated requirement is that resume must *detect a staged
  file that no longer exists and re-prompt for it, rather than silently carrying a dead reference
  into submit* — a submission referencing a deleted object is a broken clinical record.

  **D-09 (always re-require the upload) is a superset of that requirement and satisfies it by
  construction:** if a staging token is never persisted and the dropzone always returns empty, no
  dead reference can survive into submit, and no existence check against GCS is needed. The planner
  must **not** implement a staged-file existence probe — it would be dead code under D-09. But the
  planner MUST include a test proving no staging token or file reference is ever written to the
  draft, so the guarantee is enforced rather than assumed.

  Note the clocks line up in the safe direction anyway: the 24-hour draft expiry (D-05) is shorter
  than the 2-day `pending/` lifetime, so a live draft can never outlive its staged object. That is a
  helpful coincidence, **not** the mechanism — D-09 is the mechanism, and the test above is what
  holds it.

### Claude's Discretion

- Storage key naming, serialization format, and schema-version field for forward compatibility
- Where the feature-detect (D-01) lives and how it is surfaced to `QuizContainer`
- Debounce / write-frequency strategy for persisting answers as the patient progresses
- Exact neutral copy wording for the resume offer, within D-06's no-identity constraint
- Whether the 24-hour clock (D-05) is enforced on write, on read, or both

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- **`app/components/quiz/QuizContainer.tsx:68–85`** — twelve `useState` hooks hold the entire intake
  state: `step` (`FlowStep`), `patientState`, `patientInfo`, `answers`, `currentPartIndex`, `score`,
  `scoreBracket`, `symptomProfileId`, `consentChecked`, `startTime`, plus two error/UI flags. This is
  the serialization surface. `patientInfoShowErrors`, `submissionError`, and `showTestMode` are
  transient UI state and should **not** be persisted.
- **`FlowStep` union at `QuizContainer.tsx:32`** — the flow position to restore. Restoring a
  `FlowStep` that no longer exists in a future build is the obvious forward-compat hazard; a schema
  version field is warranted (Claude's discretion).

### Established Patterns

- **No storage code exists anywhere in the codebase.** `grep` for `localStorage`, `sessionStorage`,
  and `indexedDB` across `app/` and `extensions/` returns nothing. This is a **greenfield surface** —
  there is no existing pattern to follow and no prior art to be consistent with.
- **Committed build artifact.** `public/quiz-bundle.js` is checked in and rebuilt via
  `npm run build:theme`. Any quiz-source change in this phase requires a rebuild, and
  `tests/quiz-bundle-freshness.test.ts` guards it — including the Phase 4.1 block asserting the
  built `QUIZ_PARTS` order.
- **Deployment is three-channel and verified on served bytes, never on exit codes** — the
  established discipline from Phases 1, 3, and 4.

### Integration Points

- `QuizContainer` is the single integration point: it owns every piece of state to persist and every
  transition that should trigger a write (D-07) or a clear (D-08).
- The resume offer is a new pre-`state_gate` surface, or a new `FlowStep` — planner's call.
- **`branch`: Phase 04.2 work is on `phase-4.2-resume-in-progress-intake`, branched from
  `phase-4.1-testing-first-quiz-order`, NOT from `main`.** This is deliberate and load-bearing: a
  theme rebuild from a `main`-based tree would silently revert the 04.1 reorder in the shipped
  bundle. Verified at branch creation — `QUIZ_PARTS` leads with `PART7_ALLERGY_TESTING` and the
  order guard is present.

</code_context>

<specifics>
## Specific Ideas

- Resume offer copy, per D-06: neutral, no identity. Andrew accepted the bare-neutral form over the
  timestamped variant (*"...from 3 hours ago"*), so the offer need not display elapsed time.
- The upload dropzone on a resumed `had_testing` session should carry copy that explains the file
  specifically was not kept — not a generic empty state. The patient filled that field once and will
  otherwise read the empty dropzone as a bug.

</specifics>

## Deferred Ideas

- **Move the quiz to a first-party surface via a Shopify App Proxy.** Would make storage first-party
  in every browser and retire D-01/D-03 entirely. Rejected for this phase as an architecture change
  beyond the boundary. Worth its own phase if D-03's measurement shows third-party storage failing
  for a meaningful share of patients — it is also the durable fix for the
  `frame-ancestors *` clickjacking exposure already deferred to Phase 8.
- **Storage Access API prompt.** Rejected here on completion-rate grounds (D-02). Revisit only if
  Safari share is material and the App Proxy route is rejected.
- **Cross-device resume** (server draft store + emailed magic link). Already scoped and dropped
  project-wide; recorded here only so nobody re-derives it.

</deferred>
