## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] schemaFingerprintFor leaked the file_multi question's id into stored data**
- **Found during:** Task 3 (writing the D-11 write-path test)
- **Issue:** The plan's literal fingerprint formula (`items.map(item => item.kind + ":" + item.id + ":" + type).join("|")`) applied to `ALL_ITEMS` embeds the real `testing_files` question id into `currentSchemaFingerprint()`'s output. Because `writeDraft` always stamps `schemaFingerprint` into the stored JSON, every successful write's raw serialized string contained the substring `"testing_files"` — making Task 3's own required acceptance check ("`testing_files` occurs 0 times in the raw serialized string") impossible to satisfy no matter how thoroughly `answers` was stripped.
- **Fix:** `schemaFingerprintFor` now filters out `file_multi`-typed questions before mapping, using the same type-driven discipline as `stripFileTokens` (never a hardcoded ID literal). This costs no restoration accuracy: D-09 already re-requires the upload unconditionally on every resume, so a schema change scoped to a `file_multi` question can never cause a resumed draft to misrestore — the fingerprint doesn't need to be sensitive to it.
- **Files modified:** `app/lib/quiz/draft-store.ts`
- **Verification:** `npx vitest run app/lib/quiz/draft-store.test.ts` — all 14 tests pass, including the D-11 write test asserting zero occurrences of both `testing_files` and `tok_alpha_1`; fingerprint sensitivity tests (item removal, type mutation on a non-file question) still pass, confirming the fingerprint remains structurally sensitive to everything except file-upload questions.
- **Committed in:** `7e7db0a` (Task 3 commit)

**2. [Rule 1 - Bug] Test-writing wording accidentally tripped the file's own source-text gates**
- **Found during:** Task 2/3 (writing doc comments in `draft-store.ts`)
- **Issue:** Two doc-comment sentences literally contained the forbidden substrings `console.` (in "must never call `console.*`") and `typeof window.localStorage` (in "never a `typeof window.localStorage !== \"undefined\"` shortcut") and `testing_files` (in a defence-in-depth comment example) — each of which the plan's own automated verification checks for zero occurrences of, since those checks scan the whole file text, not just executable code.
- **Fix:** Reworded all three comments to describe the same constraints without using the literal forbidden substrings.
- **Files modified:** `app/lib/quiz/draft-store.ts`
- **Verification:** The plan's Task 2 verify script (console./testing_files/typeof-shortcut zero-occurrence checks plus the nine-export check) passes.
- **Committed in:** `4f413d1` (Task 2 commit, before the file was ever committed with the violation)

## Issues Encountered
- jsdom's `Storage` methods are defined on `Storage.prototype`, not as own properties of the `window.localStorage` instance. `vi.spyOn(window.localStorage, "setItem")` creates a spy but does not intercept calls made through `window.localStorage.setItem(...)` — confirmed by a disposable in-session debug test before fixing the real suite. Resolved by spying on `Storage.prototype` methods instead throughout `draft-store.test.ts`.
