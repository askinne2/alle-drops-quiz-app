# Phase 04.2: Resume In-Progress Intake - Research

**Researched:** 2026-08-10
**Domain:** Browser-local persistence (Web Storage API) inside a cross-origin iframe, for a PHI-bearing clinical quiz
**Confidence:** MEDIUM overall — HIGH on the codebase/architecture findings (all read directly from source), LOW-to-MEDIUM on D-03's live cross-browser storage behavior (no browser tool available this session; see the dedicated section below)

## Summary

This phase is architecturally small and lives almost entirely in the Browser/Client tier: one new pure
module (`app/lib/quiz/draft-store.ts`), a handful of new `useEffect`/state wiring points inside
`QuizContainer.tsx`, one new `FlowStep` value (`"resume_offer"`), and zero backend or database changes.
No new npm dependency is needed or recommended — the raw `window.localStorage` API plus ~100 lines of
pure, testable logic is sufficient, and adding a persistence library here would trigger the Package
Legitimacy Gate and CLAUDE.md's "ask before new dependency" rule for no real benefit (see `## Don't
Hand-Roll`).

The single hardest technical question this phase raises — whether third-party/partitioned storage
inside the cross-origin iframe actually works for a returning patient — **cannot be answered from this
research session alone.** No browser automation tool was available. What this document provides instead
is (a) the documented, sourced per-engine policy for third-party `localStorage` as of 2026, with explicit
confidence tags, and (b) a concrete, runnable measurement harness against the real deployed storefront
page so a human can close the gap before planning is trusted. The reasoning below (see the dedicated D-03
section) concludes that **even under the most restrictive documented partitioning models, this phase's
specific use case — same patient, same browser, same top-level storefront page — should not be broken by
partitioning itself**, because partition keys are stable across visits to the same top-level site. The
real open risk is Safari's *ephemeral* third-party storage (cleared on app relaunch) and a minority of
users who have fully disabled third-party storage (which throws), both of which D-01's silent-degrade
policy already covers by design — the harness exists to convert that reasoning into a measurement.

**Primary recommendation:** Build a single pure module (`app/lib/quiz/draft-store.ts`) that performs a
real write-read-remove canary check (not a `typeof` check) for storage availability, serializes the raw
(unfiltered) `answers` state minus any `file_multi`-typed keys, stamps a structural schema fingerprint
and a `savedAt` timestamp, and returns `null` uniformly for every "no valid draft" reason (unavailable,
absent, expired, schema-mismatched, or malformed) so `QuizContainer` never needs to distinguish why —
matching the UI-SPEC's explicit requirement that the D-01 and "no draft" paths be indistinguishable.
Wire it into `QuizContainer.tsx` at the four points the CONTEXT.md decisions already specify (first real
answer, every subsequent answer/navigation debounced, successful submit, and the "Start over" control),
and add a D-10 parity test that proves resumed and single-sitting payloads are deep-equal except for the
named wall-clock-derived fields.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**D-01 — Degrade silently when storage is unavailable.** Feature-detect writable local storage on load.
If it is not writable, never show the resume offer and never promise persistence — the patient gets
today's exact behavior. No error, no warning, no permission prompt.

**D-02 — Do NOT use the Storage Access API, and do NOT move the quiz to a first-party surface in this
phase.** Both were considered and rejected. The Storage Access API would put a browser permission
dialog on a clinical intake page before the patient has typed anything. Moving the quiz same-origin via
a Shopify App Proxy is an architecture change beyond this phase's boundary — deferred.

**D-03 (OPEN — measurement, not a preference).** Whether third-party storage actually survives in the
iframe is unresolved and must be measured, not assumed. See the dedicated section below — this research
session could not close it; it hands off a runnable harness instead.

**D-04 — Persist the full intake state, including identity PHI** — name, DOB, email, phone, plus all
quiz answers and flow position. Chosen over the narrower "symptom answers only" option, with the
shared-device trade-off explicitly accepted. This is an informed choice, not drift; D-06/D-07 are the
non-optional mitigations that make it defensible.

**D-05 — 24-hour expiry.** A draft older than 24 hours is treated as absent and cleared. No countdown,
no "expires in" copy.

**D-06 — The resume offer must reveal NO identity.** Neutral copy only. Stored identity is written back
into the form only after the patient chooses Resume.

**D-07 — First write happens on the first real answer to a quiz question.** The state gate and
patient-info typing leave nothing on disk.

**D-08 — Clear on successful submission, and an explicit "start over" control clears on demand.**

**D-09 — Restore all answers; always re-require the file upload.** Uploaded file bytes and the staged
GCS token are not persisted. The 04.1 upload wall must survive resume.

**D-10 — Resume must be clinically inert.** Same answers must produce a byte-identical submit payload
and identical score whether completed in one sitting or resumed. Fields that legitimately differ
(`completion_time`, wall-clock timestamps) must be explicitly excluded and named.

**D-11 — Do NOT build a staged-file existence probe against GCS.** D-09 closes the dead-staged-file
hazard by construction. A test proving no staging token is ever persisted is required instead.
`PENDING_OLM_AGE_DAYS = 2` (48h) vs the 24h draft expiry is a coincidence, not a mechanism.

### Pattern 1: Pure storage module, null-collapsing every "no draft" reason

**What:** `draft-store.ts` follows the exact convention already established by `schema.ts`,
`navigation.ts`, and `redirects.ts` in this codebase: named exports only, no React import, nothing
throws outward, safe defaults everywhere. `readDraft()` returns `Draft | null` and folds every failure
mode (storage unavailable, missing key, corrupt JSON, schema mismatch, expired, structurally invalid)
into the same `null` — so the caller (`QuizContainer`) has exactly one branch to write, matching
04.2-UI-SPEC.md's explicit requirement that the D-01 and "no draft" code paths be indistinguishable, or
ideally the same branch.

**When to use:** Any time `QuizContainer` needs to know "is there a valid draft to offer."

**Example:**
```typescript
// app/lib/quiz/draft-store.ts (recommended shape — not existing code)
const DRAFT_KEY = "alledrops_quiz_draft_v1";
const EXPIRY_MS = 24 * 60 * 60 * 1000; // D-05

export function isStorageAvailable(): boolean {
  try {
    const probe = "__alledrops_storage_probe__";
    window.localStorage.setItem(probe, "1");
    const ok = window.localStorage.getItem(probe) === "1";
    window.localStorage.removeItem(probe);
    return ok; // catches BOTH throw-on-access AND silent-no-op engines (see D-03 section)
  } catch {
    return false;
  }
}

export function readDraft(currentFingerprint: string): Draft | null {
  if (!isStorageAvailable()) return null;
  try {
    const raw = window.localStorage.getItem(DRAFT_KEY);
    if (!raw) return null;
    const parsed = JSON.parse(raw) as Partial<Draft>;
    if (parsed.schemaFingerprint !== currentFingerprint) return null; // stale-shape guard
    if (typeof parsed.savedAt !== "number" || Date.now() - parsed.savedAt > EXPIRY_MS) {
      window.localStorage.removeItem(DRAFT_KEY); // active cleanup, not just ignore
      return null;
    }
    if (!parsed.answers || Object.keys(parsed.answers).length === 0) return null; // D-07 defense-in-depth
    return parsed as Draft;
  } catch {
    return null; // malformed JSON, quota errors on removeItem, anything unexpected
  }
}
```

### Pattern 2: Type-driven strip list, not an ID literal (D-11)

**What:** Strip any answer key whose corresponding `QuizItem` has `type === "file_multi"` before
serializing — not a hardcoded `["testing_files"]` list. This matches the codebase's own established
anti-hardcoding discipline (SCH-02: "no question-ID literals remain"; `visibleAnswers`'s own doc comment
in `schema.ts` explicitly frames itself as a blacklist keyed off item metadata, not option-value
strings).

**When to use:** Every write to the draft.

**Example:**
```typescript
// Source: pattern derived from app/lib/quiz/schema.ts's visibleAnswers (existing code, same file
// this new function should live beside)
import { ALL_ITEMS } from "./questions";
import { isQuestion } from "./schema";

export function stripFileTokens(answers: QuizAnswers): QuizAnswers {
  const fileQuestionIds = new Set(
    ALL_ITEMS.filter((item) => isQuestion(item) && item.type === "file_multi").map((item) => item.id)
  );
  const result: QuizAnswers = {};
  for (const [id, value] of Object.entries(answers)) {
    if (!fileQuestionIds.has(id)) result[id] = value;
  }
  return result;
}
```

### Anti-Patterns to Avoid

- **Persisting `visibleAnswers()` output instead of raw `answers`.** `visibleAnswers` is the D-03
  boundary filter for the *payload/score* sites only (per its own doc comment in `schema.ts`). If the
  draft persists the filtered form, a patient who answers `med_list`, goes back, and temporarily hides
  it (flips `taking_meds` to "no") loses that typed text on the next debounced write — a real regression
  relative to today's in-memory-only behavior, which explicitly keeps hidden answers in state for this
  exact reason (see the comment at `QuizContainer.tsx:106-109`).
- **A `typeof window.localStorage !== "undefined"` feature-detect.** Insufficient — several documented
  engine behaviors leave the object present but non-functional (throws on `.setItem`, or accepts writes
  that silently don't round-trip). Must be a real write-read-remove canary (Pattern 1 above).
- **Persisting `score`/`scoreBracket`/`startTime`.** All three are either derivable (score/bracket, from
  `answers`) or actively harmful to persist (`startTime`, which would make a resumed `completion_time`
  measure days instead of minutes). See Finding 1 for the full per-field table.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Reliable storage-availability detection | A `typeof` or `try { localStorage } catch` shortcut | A real write-read-remove canary (Pattern 1) | The shortcut misses silent-no-op engines entirely — see D-03 findings on Safari's documented ephemeral/partitioned behavior, which may not throw at all |
| Debounced writes | A custom RxJS-style observable pipeline | A single `setTimeout`-based debounce (~8 lines) | One call site, no async coordination complexity needed |
| Deep equality for the D-10 test | A hand-rolled recursive `deepEqual` | `vitest`'s built-in `expect(a).toEqual(b)` (already used throughout this test suite) | Already the project's established assertion style — no new utility needed |

**Key insight:** this phase's "don't hand-roll" risk runs in the opposite direction from most phases —
the temptation here is to reach for a *library* (a persistence/state-management package) for a problem
that is genuinely small enough to hand-write correctly, and hand-writing it keeps the phase inside its
"zero new dependency" footprint, which matters given this app's PHI-handling posture and CLAUDE.md's
explicit caution about new third-party dependencies.

## Must-Investigate Findings

### Finding 1 — The serialization surface (definitive keep/drop list)

Read directly from `app/components/quiz/QuizContainer.tsx:68-85` (twelve `useState` hooks):

| Field | Persist? | Reasoning |
|-------|----------|-----------|
| `step` (`FlowStep`) | Persist, **narrowed** to `"quiz_parts" \| "consent"` | Per 04.2-UI-SPEC.md's Flow Contract, these are the only two architecturally reachable restore targets (D-07 guarantees a draft can never exist while on `state_gate`/`patient_info`). Store which of the two applies so a patient who reached `consent` isn't wrongly dropped back into `quiz_parts`. |
| `patientState` | **Persist** | Feeds `buildPayload`'s `state` field; needed to reconstruct an identical payload (D-10). |
| `patientInfo` (name/dob/email/phone) | **Persist** | D-04's explicit, deliberate choice. |
| `patientInfoShowErrors` | **Drop** | Transient validation-display UI flag, not data — confirmed transient by CONTEXT.md's own code_context notes. |
| `answers` | **Persist, minus `file_multi`-typed keys** | Core of what's being resumed. Persist the *raw* (unfiltered) object, matching the existing in-memory retention discipline QuizContainer already documents for hidden answers (`:106-109`) — do not persist `visibleAnswers()` output (see Anti-Patterns). Strip file tokens per Pattern 2 (D-11). |
| `currentPartIndex` | **Persist** | Needed to restore flow position within `quiz_parts`; not derivable from `answers` alone (a part could be entered with zero answers yet, or a patient could navigate backward non-linearly). |
| `score` | **Drop, recompute** | Recommend recomputing via the same `calculateTotalScore`/`getScoreBracket` call `goToConsent()` already makes, at restore time if `draft.step === "consent"`. Never trust a persisted numeric score — this is the more direct D-10-consistent design (score is *always* derived from current answers + current scoring logic, exactly matching the never-interrupted path, not a value that could go stale between write and read even within the same schema-fingerprint window). |
| `scoreBracket` | **Drop, recompute** | Same reasoning as `score`. |
| `symptomProfileId` | **Persist** | Generated once, before `quiz_parts`, via `generateSymptomProfileId()` = `` `AOD_${Date.now()}` `` (confirmed at `app/lib/quiz/scoring.ts:90-92`). Must be **added to D-10's named-exclusion list** (see Finding 3) — it is time-derived, so a resumed run's freshly-generated-at-a-different-moment ID would differ from a one-sitting run's ID for reasons that have nothing to do with resume mechanics, exactly like `completion_time`/`quiz_date` already do. If persisted (recommended, so a resumed session doesn't need to regenerate), it stays *stable* across the draft's own lifetime, which is the correct behavior for avoiding accidental double-generation within one resume cycle. |
| `consentChecked` | **Drop — do not restore as `true`** | Not explicitly locked by CONTEXT.md; **flagged as an Open Question below** for explicit confirmation, but the strong recommendation is to always require an active, fresh re-check on every session, even a resumed one landing directly on `consent`. ### Finding 2 — Schema versioning

Phase 4.1 just reordered `QUIZ_PARTS` (`app/lib/quiz/questions.ts:595-603`, confirmed by reading the
current file — `PART7_ALLERGY_TESTING` now leads). A stale draft written against a prior deploy's
`questions.ts` shape (different part order, a renamed/removed question ID, a changed `type`) restored
into the *current* shape is a direct D-10 violation risk: `currentPartIndex` could point at the wrong
part, or `answers` could carry an ID no live question recognizes.

**Recommendation:** derive a structural fingerprint from the live `QUIZ_PARTS` at read/write time —
e.g. a hash (or even an unhashed joined string, given the payload is tiny and this never leaves the
browser) of `ALL_ITEMS.map(item => `${item.kind}:${item.id}:${item.kind === "question" ? item.type :
""}`).join("|")`. This is self-maintaining: it changes automatically whenever a question is added,
removed, renamed, or retyped, with zero risk of a human forgetting to bump a manual constant — which
this project has a *documented, repeated* failure mode around (six UAT defects to date, several from
exactly this class of "forgot to update X when Y changed" mistake, per STATE.md's Accumulated Context).
A manual version constant is the fallback if the planner prefers the simpler approach, but it should be
paired with a guard test (mirroring `quiz-parts-order.test.ts`'s existing discipline) that fails loudly
if `QUIZ_PARTS`'s shape changes without the constant being bumped in the same commit.

**On mismatch:** discard silently, exactly like "no draft found" (D-01) — full discard, no partial
restore attempt, and actively call `localStorage.removeItem` so a permanently-stale draft doesn't linger
forever (not required by D-05, but cheap hygiene).

### Reasoning: is partitioning itself a problem for this phase?

**No — reasoned as harmless for this specific use case, with the caveat that this reasoning is
ASSUMED/derived, not measured.** Every documented partitioning model above keys the storage partition to
the pair *(top-level site, iframe origin)*, not to a session, a random value, or anything that changes
between visits. This phase's patient always returns to:
- the **same top-level site** (`allergist-on-demand.myshopify.com`, or whichever storefront embeds the
  quiz — not a different site), and
- the **same iframe origin** (`alle-drops-quiz-app.fly.dev`).

Since both halves of the partition key are identical across visits, the partitioned store the patient
wrote to on visit 1 is the **same** partitioned store they read from on visit 2 — partitioning isolates
*different* top-level sites from sharing one iframe's storage with each other, which is a non-problem
for a single patient returning to one storefront in one browser. **The real risks are orthogonal to
partitioning itself:** Safari's *ephemeral* clearing (tied to app-relaunch, not to the 24h D-05 window —
a patient who force-quits Safari between visits could lose the draft in under 24 hours, which is a
silent, D-01-covered degradation, not a bug), and the minority of users/engines that block storage
outright (also D-01-covered). **This reasoning could be wrong if any documented behavior above is
inaccurate or has changed** — hence the harness below, not a closed conclusion.

## Common Pitfalls

### Pitfall 1: Persisting the payload-boundary-filtered answers instead of raw answers
**What goes wrong:** A patient who temporarily hides an answer (e.g., flips `taking_meds` from "yes" to
"no", hiding `med_list`) loses that typed text on the next debounced write, even though today's
in-memory-only behavior explicitly preserves it for exactly this reason.
**Why it happens:** `visibleAnswers()` is the obvious-looking function to reach for since it's already
imported in `QuizContainer.tsx`, but it exists for a different boundary (payload/score construction),
documented explicitly in its own doc comment in `schema.ts`.
**How to avoid:** Persist raw `answers` (minus file tokens per Pattern 2), never `visibleAnswers()`
output.
**Warning signs:** A test that answers a question, hides it, reloads with a fresh mount from the draft,
and asserts the hidden answer's value survived would fail if this pitfall is present.

### Pitfall 2: Insufficient feature-detection
**What goes wrong:** `typeof window.localStorage !== "undefined"` returns `true` on engines where the
object exists but access silently fails or doesn't round-trip, so D-01's silent-degrade promise breaks
silently in the *opposite* direction — the app tries to persist, appears to succeed, and later can't
read the draft back, or worse, shows a resume offer for a draft that then fails to actually restore.
**Why it happens:** The shortcut is the first thing most engineers reach for.
**How to avoid:** Real write-read-remove canary (Pattern 1), tested against both throw and silent-no-op
simulated branches (Finding 6).
**Warning signs:** Any test asserting storage-availability solely from `typeof` rather than an actual
round-trip.

### Pitfall 3: A version constant nobody remembers to bump
**What goes wrong:** `QUIZ_PARTS`/`questions.ts` changes shape (exactly as it just did in Phase 4.1)
without the draft's schema version being bumped, so a stale draft from before the change gets restored
into the new shape — `currentPartIndex` could point at the wrong part, or a persisted answer ID could no
longer resolve via `getQuestionById`.
**Why it happens:** This project has six prior UAT defects on record, several from exactly this
"remembered-to-change-X-but-not-Y" class (per STATE.md's Accumulated Context — the progress-counter
defect, the stale-bundle defect, etc.).
**How to avoid:** Prefer the derived structural fingerprint (Finding 2) over a hand-maintained constant.
If a manual constant is used instead, pair it with a guard test.
**Warning signs:** A test that changes `QUIZ_PARTS`'s shape (add/remove/rename an item) without touching
the fingerprint/version logic, and asserts a previously-valid draft is now correctly rejected.

### Pitfall 4: Trusting a persisted score/scoreBracket
**What goes wrong:** If scoring logic (`calculateTotalScore`, `getScoreBracket`, or which questions are
in `ALL_SCORED_QUESTIONS`) ever changes without also changing the structural fingerprint (e.g., a
scoring-weight tweak to an *existing* question, which the ID/type-based fingerprint in Finding 2
wouldn't detect), a persisted score could silently diverge from what the current logic would compute —
a direct, hard-to-detect D-10 violation.
**How to avoid:** Never persist `score`/`scoreBracket`; always recompute from restored `answers` at the
moment they're needed (mirroring exactly what the never-interrupted path already does in `goToConsent`).
**Warning signs:** Any code path that reads `draft.score` instead of calling `calculateTotalScore` fresh.

### Pitfall 5: Forgetting the theme bundle rebuild
**What goes wrong:** `public/quiz-bundle.js`/`.css` are committed build artifacts, built by `npm run
build:theme` (a *separate* Vite config from `npm run build`), and nothing in CI runs that build
automatically. This exact mistake has shipped an invisible no-op to the storefront **at least once
already** on this project (the session-28 incident referenced throughout `tests/quiz-bundle-
freshness.test.ts`), and every phase since has needed to extend that freshness-guard file with new
presence/absence markers.
**How to avoid:** Run `npm run build:theme`, verify determinism (build twice, compare SHA-256, matching
every prior phase's documented practice in `tests/quiz-bundle-freshness.test.ts`), and add new Phase
4.2 markers (e.g., a string unique to the resume-offer copy, present-after/absent-before, counted with
`SOURCE.split(needle).length - 1`, never `grep -c` — this project has been burned by the line-vs-
occurrence trap four separate times per that file's own header comment).
**Warning signs:** A phase-gate check that only runs `npm test` and `npm run typecheck` without also
confirming the committed bundle's byte size or hash changed.

### Pitfall 6: Unthrottled writes on every keystroke
**What goes wrong:** Several Part 6/Part 7 questions are free-text (`med_list`, `current_medications`,
`history_surgeries`, `history_allergies`, `history_conditions`, `testing_year`, `testing_location`,
`testing_allergens`) and fire `onChange` per keystroke. `localStorage.setItem` is synchronous; writing
the entire draft object on every keystroke across a patient typing several sentences is wasteful and,
on some engines/devices, can introduce input jank.
**How to avoid:** Debounce the write effect (~500ms trailing), not per-field — matches CONTEXT.md's own
"Claude's Discretion" framing of this exact question.
**Warning signs:** A test spying on `localStorage.setItem` call count while simulating rapid keystrokes
into a text field, expecting far fewer calls than characters typed.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-------------------|
| V2 Authentication | No | This phase adds no authentication surface |
| V3 Session Management | No | No new server-side session concept; the "draft" is not a session token |
| V4 Access Control | No | No new access-controlled resource — the draft is client-local and readable only by the same-origin/same-partition script that wrote it, which is the browser's own access-control model, not this app's |
| V5 Input Validation | **Yes** | Schema-fingerprint + shape validation on every `readDraft()` call (Finding 2) is exactly ASVS V5's "validate all untrusted input" applied to a value the app itself wrote in a *possibly different, possibly stale* deploy — treat a stored draft as untrusted input, not as trusted internal state, because it crosses a deploy-version trust boundary even though it never crosses a network boundary |
| V6 Cryptography | No — **named limitation, not a control** | `localStorage` is not encrypted at rest by the browser. The draft (containing name/DOB/email/phone/answers) sits in plaintext on the patient's device for up to 24 hours. This is not a gap this phase can close (the Web Storage API has no encryption primitive, and adding a client-side encryption layer for a key that must also live client-side buys negligible real protection against the actual threat model — a person with physical/logged-in access to the same browser profile). D-04/D-05/D-06/D-07/D-08 are the actual mitigations, and they are UX/lifecycle controls, not cryptographic ones. State this plainly rather than implying V6 is satisfied by omission. |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| Shared/family device sees a prior patient's PHI via the resume offer | Information Disclosure | D-06 (zero identity on the offer screen) + D-05 (24h expiry) + D-08 (explicit clear) — already fully specified, this phase's core design problem |
