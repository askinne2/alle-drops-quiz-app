# Phase 04.1: Testing-First Quiz Order - Context

**Gathered:** 2026-08-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Move the existing allergy-testing part (`PART7_ALLERGY_TESTING` — the two-option split, the three
`had_testing` text fields, and the required multi-file upload) from last position to first in
`QUIZ_PARTS`, so a patient who cannot supply allergy test results discovers that in the first ~30
seconds instead of after a completed ten-minute clinical intake.

**This is a presentation-order change.** The upload endpoint (`POST /api/quiz/upload`), GCS staging
and promotion, the `submission_files` join table, and all three retrieval surfaces (embedded admin,
patient ledger, clinical PDF) are position-independent and are NOT touched.

**In scope:**
- Reorder `QUIZ_PARTS` to `[P7, P1, P2, P3, P4, P5, P6]`
- Amend the `DEC-medical-history-before-testing-split` locked decision in place
- Repoint the three test files that hardcode literal part indices
- Filter `TESTING_ANSWER_KEYS` out of the "Symptom Responses" loop in both PHI renderers (D-05)
- Record the `PENDING_OLM_AGE_DAYS` analysis in the retention doc without changing the value (D-03)
- Rebuild `public/quiz-bundle.js` in the same commit, proven by a relative-position assertion (D-09)
- Three-channel deploy and served-bytes verification (D-10)
- Blocking human browser pass (D-08)

**Out of scope:**
- Any change to `PART7_ALLERGY_TESTING`'s internal item order (D-07)
- Any change to the upload widget, `/api/quiz/upload`, GCS, promotion, or retrieval routes
- Any scoring change — impossible by construction, `ALL_SCORED_QUESTIONS` is an explicit Parts 1–5
  concatenation independent of `QUIZ_PARTS`
- Changing the live `PENDING_OLM_AGE_DAYS` value — that decision belongs to Phase 4.2 (D-03)
- localStorage / resume behavior — Phase 4.2

</domain>

<decisions>
## Implementation Decisions

### Locked-decision conflict

- **D-01:** `DEC-mandatory-allergy-testing`'s sibling, **`DEC-medical-history-before-testing-split`**
  (status LOCKED, dated 2026-07-29, sourced to the William Miller call), is **amended in place, not
  fully retracted.** Its position clause — *"The medical history section moves before the
  allergy-testing split"* — is superseded by Phase 4.1. Its **clinical rationale survives unchanged**:
  *"even a patient who books a consult directly still needs history on file for Dr. Sullivan"* is a
  statement about every patient **reaching** medical history, and that remains true — Part 6 is in
  `QUIZ_PARTS` and reached by 100% of patients regardless of where the testing split sits. The
  position clause existed because, pre-Phase-3, `setStep("medical_history")` was reachable only
  through the proceed-without-testing bypass; that bypass was deleted in Phase 3 (D-11), so the
  clause is now protecting against a failure mode that no longer exists.

  **Mechanics:** add a dated amendment block to the decision in `.planning/PROJECT.md` — same
  strike-through-and-explain convention as `DEC-testing-results-by-email-not-upload` and the
  `injectIframe` "dead code" correction — so anyone who read the original sees that it changed and
  why. **Do NOT delete the original text.** This is explicitly **not** a William blocker; no client
  response is required before building.

- **D-02:** New part order is **`[P7, P1, P2, P3, P4, P5, P6]`** — exactly one array element moves.
  Medical history (Part 6) stays immediately before consent. Rejected: `[P7, P6, P1–P5]` (two
  elements move, larger diff for no measured benefit) and the "keep the order, add an up-front
  pre-check screen" alternative (rejects the phase's premise; recorded as considered).

### GCS pending-upload retention

- **D-03:** `PENDING_OLM_AGE_DAYS` **stays at `2`** through Phase 4.1. The live lifecycle rule on
  `gs://alledrops-quiz-uploads-dev` (`{ "age": 2, "matchesPrefix": ["pending/"] }`) is **not
  changed by this phase.** What 4.1 owes is the written analysis, added to
  `docs/gcs-lifecycle-and-retention.md`: after the reorder, *every* abandoning patient leaves a
  staged object under `pending/`, not just those who reached the final part, so orphaned PHI at rest
  becomes the common case rather than the rare one. **Phase 4.2 owns the value decision**, because
  the correct window depends on how long a resuming patient must still be able to find their staged
  file. ROADMAP's instruction that 4.1 and 4.2 set this together is honored by 4.1 supplying the
  analysis and deferring the number.

  **Constraint the planner must not lose:** GCS Object Lifecycle Management expresses `age` in whole
  **days** (integer) and runs **asynchronously** — a rule can take up to ~24h to act after its
  condition is met. `age: 1` therefore means "deleted somewhere between 24 and 48 hours." Sub-day
  windows are not expressible through OLM at all. Any 4.2 proposal for an hours-scale window needs a
  different mechanism, not a smaller `age`.

- **D-04:** Whenever the value *does* change — in 4.2 or later — the phase that changes it **applies
  the rule AND verifies it**, using plan 04-17's established pattern: apply, then read the rule back
  with `gcloud`, then prove the prefix scoping against real probe objects. Never a doc-only change,
  never deferred to a human to run later, never asserted from an exit code.

### Clinical record ordering

- **D-05:** Filter `TESTING_ANSWER_KEYS` out of the **"Symptom Responses"** loop in **both** PHI
  answer renderers (`app/lib/pdf.ts` and `app/routes/app.quiz-results.tsx`), so Part 7 answers render
  **only** in their own "Test Results" section.

  **Why this is in scope for a reorder phase:** `visibleAnswers(ALL_ITEMS, answers)` builds the
  answers object in `QUIZ_PARTS` order (`ALL_ITEMS = QUIZ_PARTS.flat()`), and `pdf.ts:87` renders
  "Symptom Responses" by iterating `Object.entries(answers)` with **no exclusion**. A separate
  "Test Results" section at `pdf.ts:97-108` then re-renders the same keys. So Part 7 answers already
  print **twice** in every clinical PDF today — a pre-existing Phase 4 defect, not one 4.1 creates.
  What 4.1 *does* create is that the duplicate copy moves to the **top** of Symptom Responses, so
  Dr. Sullivan's symptom section would open with testing status, year, location, and allergens before
  a single symptom. The filter fixes the duplication and decouples the clinical record's display
  order from `QUIZ_PARTS` in one small change.

  Rejected: pinning both renderers to a canonical sort order (more robust, larger diff, and leaves
  the duplication unless also filtered) and accepting the flip (cheapest, and the clinical record is
  worse for it).

- **D-05a — AMENDED 2026-08-10, after pattern mapping.** D-05 as first written was **safe for the
  PDF and destructive for the admin modal**, and is corrected here in place rather than rewritten.
  `app/lib/pdf.ts` has *both* loops — Symptom Responses (`:85-94`) and a dedicated Test Results
  section (`:97-108`). **`app/routes/app.quiz-results.tsx` has no Test Results section at all**; its
  Symptom Responses loop (`:298-306`) is the *only* place Part 7 answers render in the provider's
  detail modal. Filtering `TESTING_ANSWER_KEYS` out of that loop without a destination would
  **silently delete** testing status, year, location, and allergens from the admin view.

  **Corrected instruction:** in `app.quiz-results.tsx`, **add a mirrored "Test Results" section
  first, then apply the filter** — never the filter alone. Follow that file's existing "Uploaded
  Files" conditional-section idiom (`:315-324`) so the new section matches the surrounding code.
  Both renderers must end up with the same shape: testing answers excluded from Symptom Responses
  and rendered exactly once under Test Results.

  **Acceptance criterion this generates, and it is blocking:** a test must prove that
  `testing_status`, `testing_year`, `testing_location`, and `testing_allergens` are each still
  present exactly once in the admin detail render after the change. A green suite that only asserts
  their absence from Symptom Responses would pass while the data is gone.

  This is a provider-facing admin surface, not a patient-collection surface, so the phase's
  `--skip-ui` decision still holds — no UI-SPEC is owed.

- **D-06:** The `part:` and `order:` fields on every question stay as they are — **inert and
  unrenumbered.** Nothing reads them; the only consumer repo-wide is `app/lib/quiz/scoring.test.ts:102`,
  asserting scored questions have `part <= 5`, which the reorder does not disturb. Add a banner
  comment above `QUIZ_PARTS` in `app/lib/quiz/questions.ts` recording that **array position, not the
  `part:` field, determines flow order**, so a future reader does not "fix" the mismatch. Rejected:
  renumbering (~40 question objects touched, rewritten scoring test, zero behavior change) and
  deleting the fields (widest diff, expands the phase past a reorder).

### Part 7 internals

- **D-07:** `PART7_ALLERGY_TESTING`'s internal item order is **untouched.** Part 7 is one part
  rendered as one screen, and all four `had_testing` children share the same
  `showIf: { questionId: "testing_status", equals: "had_testing" }` — so the upload field and its
  "This is required to continue" info block reveal **simultaneously** with year/location/allergens,
  not after them. `testing_status`'s subtitle already warns **before** the choice: *"If you choose
  'I've already had allergy testing,' you'll be asked to upload a copy of your results (PDF or photo)
  to continue."* The discovery cost inside Part 7 is a scroll, not a sequence of steps. Rejected:
  moving `testing_files` above the three text fields, and splitting Part 7 into two parts (adds a
  part, changes the step-counter denominator, rewrites `isPartComplete` coverage).

### Verification and deploy

- **D-08:** A **blocking** human browser pass is required before the phase can close. Six defects on
  this project have shipped past a fully green suite and been caught by Andrew clicking — including
  04-19's step-counter defect ("Step 2 of 9" → "Part 1 of 7"). A part reorder is precisely the change
  class a DOM test passes and a human notices. Andrew skipped the locally-testable pass on 04-19;
  4.1 does not repeat that.

- **D-09:** Prove the rebuilt bundle is live by asserting **relative position in the served bytes**,
  not by counting a new string. The established 0-before / ≥1-after freshness-marker technique
  **does not apply to this phase** — a pure array reorder introduces no new string;
  `testing_status`, `fileUpload__dropzone`, and every other Phase 4 marker already exist in the
  shipped v51 bundle. Instead measure `indexOf("testing_status")` against `indexOf("symptoms_nasal")`
  (or an equivalent Part 1 identifier): before, testing appears later; after, testing appears
  earlier. Add this as a guard test so a future reorder cannot silently regress the order. Rejected:
  SHA-256 identity alone (proves freshness, says nothing about correctness of order) and adding a
  string that exists only to be counted.

  **Occurrence counting rule, carried forward and non-negotiable:** count with
  `split(needle).length - 1`, never `grep -c` — `grep -c` counts matching *lines*, and this project
  has been burned by that twice (the Klaviyo "4 vs 10" error and the `apntly` / `appointly`
  wrong-needle error). Re-fetch with a cache-buster after any deploy; a single stale fetch is not
  evidence.

- **D-10:** Full **three-channel deploy** — merge, `fly deploy -a alle-drops-quiz-app`,
  `shopify app deploy`, then verify on served bytes. Same shape as plans 01-05, 03-07, and 04-19.
  The reorder carries no migration and no DDL, and it only helps patients once it is live. Rejected:
  holding the merge to ship together with 4.2 (delays the abandonment fix by 1–2 days).

### Claude's Discretion

- Plan and wave decomposition, and how many plans the phase needs.
- Whether the D-05 renderer filter lands in its own plan or alongside the reorder — either is fine
  provided both PHI renderers move together and `tests/pdf.test.ts` / `tests/answer-labels.test.ts`
  are extended rather than replaced.
- The exact identifier pair used for the D-09 relative-position assertion, provided both needles are
  measured non-zero in the same fetch (non-vacuity control) before the ordering claim is made.
- Test-file repointing mechanics — whether the literal indices in the three coupled test files are
  replaced with named constants derived from `QUIZ_PARTS` or simply renumbered.

## Existing Code Insights

### Reusable assets

- **`QUIZ_PARTS` is a plain array** (`app/lib/quiz/questions.ts:584-592`). The reorder is one element
  moving. Phase 2 made part order *data* — this is the payoff.
- **`quizFlowProgress`** (`app/lib/quiz/schema.ts:261-284`) is index-driven (`at(3 + step.index)`,
  `total = totalParts + 3`). The step counter self-adjusts; no copy or arithmetic change needed.
- **`itemsForPart`** is the pure, tested selector — `QuizContainer.tsx:187` does no filtering of its
  own, so the renderer needs no change at all.
- **`ANSWER_LABELS` / `getAnswerLabel`** (`app/lib/format.ts:20+`) already map every Part 7 key to a
  clinical label, with an unmapped-key fallback. D-05 changes *which loop* renders them, not the map.

### Established patterns (constraints)

- **Score is structurally safe.** `ALL_SCORED_QUESTIONS` (`questions.ts:562-568`) is an explicit
  Parts 1–5 concatenation, and `calculateTotalScore` is always called with it. Reordering
  `QUIZ_PARTS` cannot alter a score. **Do not create scoring tasks** — PROJECT.md says so explicitly.
- **`getQuestionById`** (`questions.ts:574-578`) resolves by `find`, so its concatenation order is
  irrelevant to the reorder.
- **`generateSymptomProfileId()`** fires on leaving `patient_info` (`QuizContainer.tsx:271`), which
  still precedes part index 0. **Verified against source, not assumed** — ROADMAP's claim holds.
- **`ALL_ITEMS = QUIZ_PARTS.flat()`** (`questions.ts:597`) feeds `visibleAnswers` at
  `QuizContainer.tsx:117,151,418`, which builds the submitted answers object. Reordering therefore
  changes the JSONB key order and, downstream, the PDF/admin display order. This is the mechanism
  D-05 exists to neutralize.
- **`part:` / `order:` fields are inert.** Sole repo-wide consumer: `scoring.test.ts:102`. Confirmed
  by grep across `app/lib/quiz/`, `app/components/quiz/`, and `app/lib/`.

### Integration points

- **`app/lib/quiz/questions.ts:584-592`** — the `QUIZ_PARTS` array literal (D-02 + D-06 banner comment)
- **`app/lib/pdf.ts:85-108`** — Symptom Responses loop and Test Results section (D-05)
- **`app/routes/app.quiz-results.tsx`** — the second PHI answer renderer (D-05)
- **`.planning/PROJECT.md` `<decisions>`** — the amendment target (D-01)

## Specific Ideas

- **Amendment wording convention (D-01):** follow `DEC-testing-results-by-email-not-upload` exactly —
  original text struck through or clearly marked superseded, a dated amendment paragraph naming
  Phase 4.1 as the superseding source, and an explicit sentence that the clinical rationale survives.
  The point of the convention is that anyone who read the original sees that it changed and why.
- **Non-vacuity is a hard requirement, not a nicety.** Every positional or occurrence assertion in
  this phase must be shown non-vacuous — measure both needles nonzero in the same fetch before
  claiming anything about their relative order. This project has shipped two separate
  count-against-the-wrong-thing errors.
- **The clinical PDF is the deliverable Dr. Sullivan actually reads.** When weighing D-05's diff
  size, weight legibility of that document over minimizing the change.

<deferred>
## Deferred Ideas

- **`PENDING_OLM_AGE_DAYS` value change** — deferred to Phase 4.2 by D-03. 4.1 supplies the analysis;
  4.2 picks the number, applies it, and verifies it per D-04.
- **Sub-day pending-object expiry** — not expressible through GCS Object Lifecycle Management
  (`age` is whole days, asynchronous, up to ~24h latency). If 4.2 wants an hours-scale window it
  needs a different mechanism — a scheduled deletion job or signed-URL expiry — which is a new
  design, not a config tweak.
- **Splitting Part 7 into two parts** (radio screen, then details + upload) — considered and rejected
  by D-07. Would give the fastest possible discovery but adds a part, shifts the step-counter
  denominator, and rewrites `isPartComplete` coverage. Revisit only if UAT shows patients missing the
  upload requirement.
- **Pinning both PHI renderers to a canonical clinical sort order** — considered under D-05 and
  rejected as larger than this phase needs. Would make the clinical record immune to *any* future
  `QUIZ_PARTS` change. Reasonable Phase 8 hardening if part order churns again.
- **Renumbering or deleting the inert `part:` / `order:` fields** — rejected by D-06 as pure churn.
  A future phase that adds a part may want to revisit, but only alongside a real consumer.
- **The pre-existing Part 7 answer duplication in the clinical PDF** — being fixed by D-05 as an
  adjacent, in-scope repair. Recorded here so its Phase 4 origin is not lost: `pdf.ts`'s Symptom
  Responses loop never excluded testing keys, and this was true before 4.1 touched anything.
- **Cross-device resume and "you left something unfinished" outreach** — out of scope for v1.0 per
  PROJECT.md; requires the server-side draft table plus an email provider, two more BAA surfaces,
  and it has never been priced.

</deferred>
