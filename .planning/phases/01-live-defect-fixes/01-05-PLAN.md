<objective>
Ship the change across all three delivery channels in the correct order, and prove each one landed by
asserting on **served bytes**.

Purpose: the code in this phase is a handful of lines against an already-proven mechanism. The risk was
never the code — it is that this phase ships across three independent delivery channels with three
different freshness characteristics, and this repo has a documented false-positive-verification
incident caused by exactly that divergence. `shopify app deploy` does not deploy the Fly app, and
`fly deploy` does not deploy the extension. Two commands, three artifacts, three freshness profiles.

Order matters and is not arbitrary. Fly goes first, then the extension. Deploying the parent handler
last means the transitional window has an **old parent**, which ignores unknown message shapes
harmlessly, rather than a **new parent** starved of the messages it recognises. The `url` → `path`
rename makes that window fail closed in either direction, but the ordering removes the need to rely on
it.

Not a single success claim here may rest on a deploy exit code, a `Cache-Control` header, or a 200 from
`/health` — `/health` returns static JSON and never touches the database. Every gate asserts on bytes
the live system actually served.

Output: three deployed channels, and passing Gates A, B, and C.
</objective>
