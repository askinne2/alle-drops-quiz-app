<decisions>
**D-52-03 — API validation is strict, the database CHECK is permissive.** `quiz-validation.ts`
accepts only the three labels this app currently produces (`0-2`, `3-8`, `9+`). It does NOT accept
`3-6` or `7+`: those exist only as history, and nothing should ever newly write them. The widened
`CHECK` in migration 005 (plan 05.2-03) is the outer bound that lets historical rows keep satisfying
the constraint — it is not a second write-path allowlist. Two guards at different widths is the
intent, not an inconsistency.

**D-52-04 — Provider surfaces read five labels, patient surfaces produce three.** Because historical
rows are never relabelled (SOURCE doc planning assumption 2), `pdf.ts` and `app.quiz-results.tsx`
must render legacy `3-6` / `7+` rows with a meaningful label rather than falling through to the
`??` default. Both maps gain the two legacy keys, marked as legacy in their display text so a
provider can tell a pre-revision row from a post-revision one at a glance.

**D-52-05 — The `/ 60` denominator stays on provider surfaces.** SOURCE doc planning assumption 1:
dropping the denominator is patient-facing only. `pdf.ts` line 82 prints `Score` as a bare number
today and gains nothing here; the admin table is unchanged in this respect. Do not remove or add a
denominator on either provider surface in this plan.
</decisions>
