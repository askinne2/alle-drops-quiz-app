## Decision: ADOPT, narrowly. Phase-level, stated here once.

**Decision:** add `jsdom` and `@testing-library/react` as **devDependencies** and write **exactly one**
new DOM test file, `tests/quiz-part-renderer-dom.test.ts`, activated per-file with a
`// @vitest-environment jsdom` docblock. The global vitest `environment: "node"` setting is NOT
changed. No runtime dependency is added. `vitest.config.ts` is NOT modified.

**Why the answer changed from Phase 2's "no":**

| Session | Defect | Suite at the time | Caught by |
|---|---|---|---|
| 32 | `public/quiz-bundle.js` never rebuilt — phase invisible on the storefront | 269 green | a human clicking |
| 32 | Container filtered info blocks out before the renderer saw them | 269 green | a human clicking |
| 33 | Exclusive option disabled every sibling; the switch was unreachable | 280 green | a human clicking |

Phase 2 declined on two data points. There are now three, and all three live in the wiring between
a correct `schema.ts` and the DOM. Phase 3 rewires that exact seam AND ships the first production
info block — the same failure shape as session 32's second defect. Declining a fourth time and
relying on source-text guards would be betting that the next defect happens to take a shape a string
count can see. The two session-32 defects did not.

**Why the scope is one file, not a test program.** The seam that has failed three times is
`QUIZ_PARTS` → `itemsForPart` → `QuizPartRenderer` → DOM. The new test renders the REAL
`itemsForPart(QUIZ_PARTS, 5)` output through the REAL `QuizPartRenderer` — which reproduces that
entire seam without fixtures. `QuizContainer` itself is deliberately NOT rendered: it reads `window`,
posts cross-origin messages, and calls `fetch`, so rendering it needs a mock surface that becomes its
own maintenance liability and its own source of false confidence. Its wiring stays guarded by
source-text assertions with positive controls (plan 03-03), which is what actually caught the
session-32 container defect once it was known.

**What this does NOT replace.** The manual browser check in plan 03-05 still happens. jsdom proves a
node exists in a tree; it cannot prove the card paints, that the accent border is visible, or that
the card is not hidden under the sticky header on a real mobile viewport. UI-SPEC.md requires that
check and this decision does not discharge it.

**Compliance:** both packages are devDependencies. They cannot reach `public/quiz-bundle.js` (built
by `vite.theme.config.ts` from `app/` sources) and cannot reach the quiz page. No runtime dependency
is added, satisfying the phase's hard constraint. Package legitimacy is gated by a blocking human
checkpoint in Task 1 — see `T-3-SC`.

**Cost accepted:** two devDependencies, one `// @vitest-environment jsdom` docblock, and a test file
that must be written without JSX (see Task 3) because the existing vitest `include` glob covers
`*.test.ts` only.
</dom_test_infra_decision>
