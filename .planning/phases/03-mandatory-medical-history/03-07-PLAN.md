<objective>
Merge the phase branch, deploy to Fly, prove the new release is actually serving, and only then
execute the `DROP COLUMN` migration — verifying it by query results, never by exit codes.

Purpose: this is the ordering constraint the whole phase is built around. `insertSubmission` names
its columns explicitly, so a `DROP COLUMN` that lands before the new code is live hard-fails EVERY
patient submission with `column "personal_history_json" of relation "submissions" does not exist`,
for as long as the old release keeps serving. Read paths degrade gracefully; the write path does not.
The asymmetry is why this is a separate wave and not an implicit dependency.

Output: a merged PR, a live Fly release proven on served bytes, the two columns gone, matching
before/after row counts, and a post-DDL submission proving the write path still works.
</objective>
