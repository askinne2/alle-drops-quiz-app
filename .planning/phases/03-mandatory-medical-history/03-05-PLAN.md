<objective>
Rebuild the committed theme bundle, extend the bundle-freshness guard with markers that can actually
detect Phase 3 staleness, run the full phase gate, and get human eyes on the two things no automated
check can prove.

Purpose: `public/quiz-bundle.js` is a committed build artifact produced ONLY by `npm run build:theme`
(a separate `vite.theme.config.ts`). `npm run build` does not touch it. Forgetting the rebuild
shipped an invisible no-op phase in session 32. Worse — and this was measured during planning — the
EXISTING `tests/quiz-bundle-freshness.test.ts` asserts only Phase-2 markers (`isAnswered`, the quoted
`"info"` kind check). Those are already present in the committed bundle, so the guard stays GREEN
against a Phase-3-stale bundle. It would not have caught this phase's staleness. That gap is closed
here.

Output: a rebuilt bundle, a freshness guard with proven Phase-3 markers, a green phase gate, and two
recorded human verifications.
</objective>

<rebuild_timing_note>
The standing project rule is "rebuild `public/quiz-bundle.js` in the same commit as any quiz-source
change." Plans 03-01, 03-03, and 03-04 each change quiz source and each deliberately skip the
rebuild. That is intentional and is recorded here rather than left implicit.

Reason: the bundle is a single ~185KB minified artifact. Rebuilding it in three separate commits
across two waves produces three large binary-shaped diffs, invites merge conflicts between the two
parallel Wave 2 plans (03-03 and 03-04 both change quiz source), and each intermediate bundle would
represent a half-finished phase that must never reach the storefront anyway. The phase deploys once
(D-14) from one branch.

The rule's PURPOSE — that no deploy ever serves stale quiz content — is preserved and strengthened:
this plan performs exactly one rebuild, adds a marker that fails against any pre-Phase-3 bundle, and
sits as a hard wave dependency in front of the deploy plan (03-07). No deploy can occur without
passing through here.
</rebuild_timing_note>
