# Phase 3 — UI Design Contract: Mandatory Medical History

> Visual and interaction contract for HIST-01…HIST-05 and DIAG-01. Generated by gsd-ui-researcher,
> verified by gsd-ui-checker. Every value below is grounded in `app/styles/quiz.module.css` as it
> exists today — there is no Tailwind, no shadcn, no component library, no design-token file
> anywhere in this repo. The only stylesheet for this surface is that one CSS Module, and the only
> "design system" is the set of CSS custom properties it declares plus the Shopify theme variables
> it reads (`--color-foreground`, `--color-background`, `--color-button`, `--font-body-size`, etc.).

---

## Design System

| Property | Value |
|----------|-------|
| Tool | **none** — shadcn gate not applicable |
| Preset | not applicable |
| Component library | none — hand-written React + CSS Modules only |
| Icon library | none — inline SVG authored in-repo, or a unicode glyph. Precedent: the checkmark icon in `QuizContainer.tsx`'s `"completed"` step (`<svg>` inline, no external asset, no icon font) |
| Font | Inherited from the Shopify theme via `var(--font-body-family, -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, "Helvetica Neue", Arial, sans-serif)` (`quizContainer` rule, `quiz.module.css:59`) and `var(--font-heading-family, var(--font-body-family, inherit))`. This app never requests a remote font — the fallback stack is system fonts only. If the theme's own font setting resolves to a hosted font, that is a theme-level configuration outside this repo and outside Phase 3's scope. |

**Why "none" and not a question to the user:** hard constraint 3 forbids any new runtime dependency
(component library, CSS framework, animation library). The shadcn gate's "ask the user" branch is
overridden by this project's compliance rules — asking would misrepresent an option that does not
exist for this codebase. Everything in this contract is expressed in plain React + the existing
`app/styles/quiz.module.css`.

## Spacing Scale

`quiz.module.css` already declares a **4px-multiple** spacing scale as CSS custom properties,
mobile-first with a tablet-and-up override (`:root` block, lines 15–47). This is the scale for
Phase 3 — no new tokens are introduced.

| Token | Mobile (< 750px) | Tablet/desktop (≥ 750px) | Usage |
|-------|-------------------|---------------------------|-------|
| `--quiz-spacing-xs` | 4px | 8px | Icon-to-text gaps, tight vertical rhythm within a linked gate/reveal pair |
| `--quiz-spacing-sm` | 8px | 12px | Compact element spacing, option-list gaps |
| `--quiz-spacing-md` | 12px | 16px | Default question-card padding, `.questionCategory__questions` gap |
| `--quiz-spacing-lg` | 16px | 24px | Section padding, spacing between the three D-06 gate+reveal groups |
| `--quiz-spacing-xl` | 20px | 32px | Layout gaps |
| `--quiz-spacing-xxl` | 28px | 48px | Major section breaks |

Exceptions for this phase: **none.** Every new class this phase adds must use one of the tokens
above, not a literal pixel value.

Accuracy correction (checker, 2026-08-09 — the original claim here was that the file contains *no*
bare `px` spacing values, which is false and was verified false against source): `quiz.module.css`
carries **four pre-existing bare-px spacing declarations** outside the token scale —
`gap: 4px` (:252), `margin-left: 6px` (:277), `margin-top: 2px` (:1684), `margin-top: 4px` (:1693).
All four are legacy and none are introduced by this phase. The 44px touch-target minimums are a
separate case: an accessibility floor, not a spacing-rhythm value.

The rule for Phase 3 stands unchanged — new classes use tokens. The legacy exceptions are recorded
so nobody later reads "the file has no bare px values," finds four, and concludes the contract is
untrustworthy.

## Typography

Values are given in `rem` because that is the unit the codebase actually uses everywhere
(`quiz.module.css` never uses `px` for font-size). The Shopify theme (Sense v15.4.1) sets the root
font-size, and this repo does not control it — do **not** assert a px conversion without a rendered
screenshot. Executor: confirm visually on the deployed page rather than trusting an assumed
10px-root conversion.

| Role | Size (mobile → desktop) | Weight | Line Height | Existing class this phase reuses |
|------|--------------------------|--------|-------------|-----------------------------------|
| Label (question/gate text) | 1.4rem → 1.6rem | 600 | browser default (~1.3) | `.questionCard__label` |
| Body (option text, textarea value, info-block paragraphs) | 1.4rem → 1.6rem | 400 | 1.5 → 1.6 | `.questionCard__optionVertical span`, `.quizContainer__input` |
| Caption / muted (subtitle, hint text under a label) | 1.2rem → 1.4rem | 400, `rgba(foreground, 0.6)` | 1.5 | `.questionCard__subtitle` |

That is 3 declared sizes and exactly 2 weights (400 / 600), matching the existing file exactly. Do
not introduce a 4th size or a 3rd weight for Phase 3 content — none of HIST-01…05 or DIAG-01 needs
one.

**Explicitly out of scope for this phase's new surfaces:** `.questionCategory__title` (1.6rem →
2rem, weight 700, line-height 1.2) — this is the Heading role and it exists in the file, but see
the Progress Indicator decision below for why Phase 3 does **not** use it.

## Color

This app has no owned color palette — every color is either a Shopify theme CSS custom property
(dominant/secondary/accent) or one of three fixed semantic hex values declared once in
`quiz.module.css:31-33`. Phase 3 introduces **zero new colors.**

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `rgb(var(--color-background, 255, 255, 255))` | Page background, every `.questionCard` background, the info-block card background |
| Secondary (30%) | `rgba(var(--color-foreground, 32, 34, 35), 0.03–0.15)` | Card borders (`0.15` at rest), dividers, tinted panels (`0.02–0.04`), the `.questionCard:hover` shadow |
| Accent (10%) | `rgb(var(--color-button, 0, 123, 255))` | **Reserved for:** selected-option border + `0.1`-opacity tint (`.questionCard__optionSelected`), focus rings, the Next/See-results/Submit buttons, the progress-bar fill gradient, and — **new in this phase** — the info-block's left border and icon stroke (see Info Block spec below) |
| Destructive | `var(--quiz-color-error, #F44336)` | The `.required` indicator only. **No destructive UI actions exist in this phase** — D-01's column-drop migration is a backend/ops action with its own on-demand-backup requirement (CONTEXT.md D-01); it has no UI confirmation flow and is out of scope for this contract |

**Accent reserved for, explicit list (no "all interactive elements" catch-all):**
1. Selected checkbox/radio option border + background tint
2. Input/select focus ring
3. The Next / See results / Submit / Previous-button-hover navigation controls
4. The progress bar fill
5. **New:** the info-block left border, its icon, and the `strong`/monospace accents already used elsewhere (profile ID, etc. — unaffected by this phase)

The info block gets the *same* accent color already reserved for interactive/selection state, not a
new color, because HIST-04's "no PCP" recommendation is the first production consumer of
`InfoBlockCard` and reusing the accent signals "read this, it matters" without inventing a fourth
palette entry. It deliberately does **not** reuse `--quiz-color-warning` (the disclaimer/caution
color) — a clinical recommendation to establish care is not a warning, and reusing warning-orange
would misrepresent its severity to a patient.

## Component Inventory — new / modified for Phase 3

No new component files are required beyond what Phase 2 already built. Everything below is either
a new CSS class in `quiz.module.css` or a data-driven usage of an existing component
(`QuizPartRenderer`, `InfoBlockCard`).

### Primary focal point (added per checker Dimension 2)

**On the medical-history screen, the eye should land first on whichever question card is currently
being answered — not on any single fixed element.** This part is a linear form, not a dashboard,
and every card is equally load-bearing clinically.

The one deliberate exception is the **HIST-04 info block when it is visible.** Its accent left
border and inline icon are the only non-neutral treatment on the screen, so when the patient
answers "no" to having a PCP, it becomes the dominant element by design — that is the entire point
of differentiating it from a question card. It must read as *"this is telling you something"* the
moment it appears, because a patient who skims past a clinical recommendation has effectively not
received it.

Nothing else on this screen competes for that role. In particular, the three D-06 gate+reveal
groups must read as **equal siblings** — no visual hierarchy between surgeries, allergies, and
other conditions. Any treatment that makes one of the three louder than the other two is wrong.

### 1. HIST-01 — 11-option comorbidity checklist (mobile layout decision)

**Use the existing `.questionCard__optionsVertical` pattern unmodified. Do not introduce a grid or
multi-column layout for this question.**

- This is the pattern already used for `yesno` and `control_0_3` questions — a single-column flex
  list, `gap: var(--quiz-spacing-xs)` mobile / `var(--quiz-spacing-sm)` desktop, each option a
  `min-height: 44px` full-width tap target (`quiz.module.css:1481-1524`).
- The alternative pattern in the file, `.questionCard__options` (the `auto-fit, minmax(100–120px)`
  grid used for `severity_0_3` / `frequency_0_4` / `bother_0_4`), was designed for short
  single-word Likert labels ("None", "Mild", "Rarely") displayed side by side. HIST-01's longest
  option — "Immune system deficiencies (acquired / induced)" — would wrap awkwardly and shrink the
  tap target in a grid column. Do not use it here.
- At 11 options the card is simply taller (~500–650px of vertical list on mobile at 44px min-height
  + `--quiz-spacing-xs` gaps). The page scrolls normally; no internal scroll container, no
  "show more" collapse, no pagination. Nothing in the codebase does that for any other question and
  introducing it here would be a new interaction pattern for one question — reject it.
- The "None of the above" option is the 11th item in the same vertical list, styled identically to
  the other ten (no visual separator, no distinct treatment) — carrying `exclusive: true` per
  CONTEXT.md D-07. **Per the standing rule from the D-13 reversal: exclusivity must never make a
  sibling option unclickable.** If any visual signal for exclusivity is added at all, it must be
  copy-only or a subtle state change on the *other* options when reselected (e.g., they simply
  toggle off, already the existing `toggleOption` behavior) — never `disabled`, never
  `pointer-events: none`, never reduced opacity implying "cannot click."

### 2. HIST-03 — the three gate + reveal pairs (grouping and spacing contract)

This is the highest-value visual decision in the phase. The goal: three coherent topics, not six
disconnected cards.

**Spacing contract:**
- **Within a pair** (gate → its revealed `text_input`): the two cards must read as one continuous
  unit. Add a new modifier class to the revealed card, `.questionCard__revealChild`, and to its
  gate, `.questionCard__gateParent`, both keyed purely off data already on the schema item — a gate
  is any item whose `id` is referenced by the *next visible item's* `showIf.questionId`; a reveal is
  any item with `showIf` + `required: false` (the exact D-06 signature, already true of every one of
  these six items and no others in the quiz). No new schema field is needed to detect this — it is
  derivable from what CONTEXT.md D-06 already declares.
  - `.questionCard__gateParent` (when its paired reveal is currently visible): `border-bottom-left-radius: 0; border-bottom-right-radius: 0; margin-bottom: 0;`
  - `.questionCard__revealChild`: `border-top-left-radius: 0; border-top-right-radius: 0; margin-top: 0; border-top: 1px dashed rgba(var(--color-foreground, 32, 34, 35), 0.15);`
  - This reuses a technique already proven in this exact file: `quiz.module.css:1763` already uses
    `:has()` for conditional styling (`.questionCard__options .questionCard__option:has(input[type="radio"]:focus-visible)`), so a sibling-aware `:has()` selector is not a new capability for this
    codebase, e.g. `.questionCard:has(+ .questionCard__revealChild) { ... }` is available as an
    alternative to a conditional class if the executor prefers not to compute the "is this a gate"
    condition in JS.
  - Net visual result: the gate card and its reveal card touch with no gap and a shared rounded
    outer edge (rounded top on the gate, rounded bottom on the reveal, flat seam between them with a
    thin dashed accent-neutral divider) — reading as one two-part card, not two cards.
- **Between the three pairs:** use the normal `.questionCategory__questions` flex gap (`--quiz-spacing-md` mobile / `--quiz-spacing-lg` desktop) — the existing uniform gap already used between
  every other item in a part. Do not add extra spacing beyond what the flex container already
  provides; the visual "seam" from the paired styling above is what separates a pair from a
  standalone gap, so no additional margin token is needed.
- **No shared section heading** across the three pairs (see Progress Indicator section below for
  why headings are avoided entirely in this phase) — the gate question text alone establishes the
  topic for each pair ("Have you had any previous surgeries?" reads as its own topic without a
  parent label).

### 3. HIST-02 — medications reveal (behavioral note only, no new visual pattern)

Uses the exact same `.questionCard__revealChild` treatment is **not** required here — HIST-02's
reveal is a single `text_input` gated on `isAnswered` against the 11-option checklist, not a
same-topic yes/no gate. Render it as a normal, standalone `.questionCard` (no linking treatment),
appearing directly after the comorbidity checklist in part order. Because the checklist is long
(11 options), the reveal will land well below the fold on mobile when it appears — this is an
accepted tradeoff (see "Reveal appearance" below), not a defect to design around.

### 4. HIST-04 info block — `InfoBlockCard` (D-09's first production consumer)

**The info block must be visually distinguishable from a question card at a glance.** Today's
`InfoBlockCard` (`QuizPartRenderer.tsx:36-54`) reuses `styles.questionCard`,
`styles.questionCard__label`, and `styles.questionCard__subtitle` verbatim — it is currently
pixel-identical to a question asking for input. That is wrong for a clinical recommendation: a
patient must not think it is asking them something, and must not skim past it as decorative text
either.

**New classes required**, all additive to `quiz.module.css`, all built from existing tokens:

- `.infoBlockCard` — replaces `.questionCard` for this component only.
  `border-left: 3px solid rgb(var(--color-button, 0, 123, 255))` (4px at ≥750px, matching the
  existing `.quizContainer__disclaimer` border-width breakpoint pattern), background
  `rgba(var(--color-foreground, 32, 34, 35), 0.02)` (a visibly different fill from a question
  card's plain white/background-color fill), same padding and border-radius as `.questionCard`,
  `display: flex; gap: var(--quiz-spacing-sm); align-items: flex-start;` to seat an icon beside the
  text.
- `.infoBlockCard__icon` — a fixed-size (20px mobile / 24px desktop) inline SVG slot, `flex-shrink: 0`, stroke color `rgb(var(--color-button, 0, 123, 255))` (the accent). Content: a simple
  circle-with-"i" glyph, hand-authored inline in `InfoBlockCard` — same technique as the existing
  checkmark SVG in `QuizContainer.tsx`'s completed step. `aria-hidden="true"` (the text alone must
  carry the meaning).
- `.infoBlockCard__heading` — reuses the Label typography role (1.4rem → 1.6rem, weight 600) but
  is a **new class**, not `.questionCard__label` — sharing the class name is exactly the bug being
  fixed. HIST-04's info block does not use a heading (see locked copy above), so this class exists
  for future info blocks (Phase 4 TEST-03) that may need one.
- `.infoBlockCard__paragraph` — reuses the Body/Caption typography role
  (`.questionCard__subtitle`'s existing 1.2rem → 1.4rem, `rgba(foreground, 0.6)`... **do not**
  reuse that exact rule as-is): use full-opacity foreground text here
  (`rgba(var(--color-foreground, 32, 34, 35), 0.85)`, matching `.quizContainer__scrollBox`'s body
  copy opacity) at the Body size (1.4rem → 1.6rem), because this text is the entire content of the
  card and must read as primary, not as a de-emphasized hint the way `questionCard__subtitle` is
  used elsewhere.
- `.infoBlockCard__bullets` — plain `<ul>`, no custom marker styling needed until a real consumer
  needs one (none does in Phase 3).

**Non-interactivity must also be structural, not just visual:** no `cursor: pointer`, no
`:hover` box-shadow (the `.questionCard:hover` rule must not apply — this is why `.infoBlockCard`
is a separate class rather than a modifier layered on `.questionCard`), and the outer element stays
a plain `<div>` with no implicit ARIA role that would suggest interactivity. Consider
`role="note"` on the outer div — it costs nothing and correctly announces "supplementary
information" to a screen reader instead of leaving the container role ambiguous.

**Verification budget, carried from CONTEXT.md D-09:** this is the first production render of
`InfoBlockCard` anywhere. Budget a manual browser check (not just a test) after HIST-04 lands —
session 32 shipped an info block that the container silently filtered out before the renderer ever
saw it, caught only by a human looking. Confirm the "no PCP" branch actually paints on a real
mobile viewport, not just that a unit test asserts the DOM node exists.

### 5. Reveal appearance — no animation

**Nothing moves.** No fade-in, no slide-down, no height transition. This is not a stylistic
choice made freely — it is required by hard constraint 3 (no animation library) and it is also
already the codebase's existing precedent: `med_list` / `med_control` (Part 5, live today) already
appear and disappear via `showIf` with zero transition wrapping the conditional render. Every new
`showIf`-gated item in Phase 3 (HIST-02's medications field, all three HIST-03 reveals, HIST-04's
two clinic fields and its info block) must render with the same abruptness — the item is simply
present or absent in `visibleItems(items, answers)`'s output on the next render, at its natural
flow position.

**Accepted tradeoff, not a defect:** because several of these reveals sit below a long preceding
question (the 11-option checklist above HIST-02's reveal is the sharpest case), a patient may not
immediately notice a new field appeared below the fold. No layout-shift mitigation (e.g., scroll-to
the newly revealed field) is in scope for this phase — it would be new interaction behavior beyond
"content plus wiring," and CONTEXT.md's phase boundary is explicit that Phase 3 adds no new
mechanism.

### 6. Progress indicator and section heading — resolved, no new copy needed

**Decision: Part 6 renders with no section heading, exactly like Parts 1–5 today.**

Verified in `QuizPartRenderer.tsx` and `QuizContainer.tsx`: **no part in the current `quiz_parts`
flow renders a category title.** `.questionCategory__title` exists in the CSS file and is used
exactly twice today — the deleted `medical_history` step's ad hoc `<h2>Medical history</h2>`
(`QuizContainer.tsx:550`, itself being deleted by D-12) and the "Thank You" completed-step heading.
Adding a heading to the new Part 6 while Parts 1–5 have none would be a new, inconsistent visual
pattern introduced for one part only. Match the established precedent: **no heading.**

**Progress label needs zero code changes.** `TOTAL_FLOW_STEPS` and the `"Part N of {quizPartsTotal}"` label (`QuizContainer.tsx:322-335`) are already computed from `QUIZ_PARTS.length`, not
hardcoded to 5. Once medical history is `QUIZ_PARTS[5]` (per CONTEXT.md's discretion on how the
sixth entry attaches), the progress bar and the "Part 6 of 6" label are correct automatically. This
is a direct consequence of Phase 2's schema work, not a new Phase 3 capability — call it out to the
planner as a task that does **not** need a line item, not as something to build.

### 7. Mobile sticky-header scroll clearance — flagged, not resolved here

**This phase does not need new scroll-handling code.** Medical history becomes `currentPartIndex`
5 within the existing `quiz_parts` step (not a separate `FlowStep`, per D-12/D-13), so it
automatically receives the same `quiz:scrollToTop` postMessage the existing `useEffect` already
fires on every `[step, currentPartIndex]` change (`QuizContainer.tsx:162-173`). No design decision
is owed here for the *mechanism*.

**What remains an open, unresolved risk** (carried from `STATE.md`'s Deferred Items table): the
receiving side of that scroll — `scroll-margin-top: 100px` — is hardcoded in
`extensions/quiz-block/blocks/symptom-quiz.liquid:25`, a **theme-repo file outside this contract's
stylesheet**, and has only ever been measured on desktop (12px clearance). It was never measured on
mobile. Adding a sixth scrollable part boundary increases the number of times a patient's viewport
could land with content hidden under a sticky header, but this UI-SPEC cannot resolve it — the fix
lives in a different repo and needs a real device/viewport measurement, not a design token.
**Recommend to the planner:** add a mobile-viewport scroll-clearance screenshot at the Part 5→6
boundary to this phase's verification checklist, using the existing unresolved 100px value; do not
treat a passing desktop check as sufficient evidence, per the same lesson Phase 1 already recorded
once for this exact offset.

## Interaction Contract Summary

| Behavior | Rule |
|----------|------|
| Exclusive option (HIST-01 "None of the above") | Selecting it deselects all siblings (existing `toggleOption`); selecting any sibling while it is active switches in one click (D-07 / the D-13 reversal). **Never render a sibling `disabled`.** |
| Required field, unanswered | Next/See-results stays disabled, silently — no new inline error copy this phase (see Copywriting Contract) |
| Conditional reveal | Appears/disappears with zero animation, at natural DOM position, the instant its `showIf` condition changes truth value |
| Hidden answer retention | A patient's typed/selected answer in a field that becomes hidden is **not** cleared (D-03, Phase 2) — flipping a gate back and forth must not lose typed text. No Phase 3 UI should imply otherwise (no "this will clear your answer" copy, because it will not) |
| Info block | Fully inert — no focus stop, no click target, no hover state, screen-reader announced as supplementary content (`role="note"`) |
