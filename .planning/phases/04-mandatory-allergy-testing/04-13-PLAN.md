    Sequence, each step in its own try/catch with a distinct `[upload]` log prefix:

    1. **Guards.** OPTIONS -> 204 with CORS headers. Non-POST -> 405 `{ error: "Method not allowed" }`.
       Restrict `Access-Control-Allow-Origin` no more loosely than `api.quiz.submit.tsx` does today;
       if that route uses `*`, match it and record in a comment that tightening it is a phase-8

    2. **Parse.** `parseFormData(request, uploadHandler, { maxFileSize: MAX_FILE_BYTES, maxTotalSize:
       MAX_TOTAL_BYTES, maxFiles: MAX_FILES })`. The caps must be passed to the parser, never checked
       after buffering — that is the entire reason this package is here.

    3. **Sniff before accepting.** Inside `uploadHandler`, read the first `MIN_SNIFF_BYTES` from the
       stream, call `sniffType`, and reject with a distinguishable failure if `isAllowedType` is
       false. Do this before any byte is written to GCS. Never consult `fileUpload.type` or the
       filename extension for the accept decision.

    4. **Convert HEIC.** If the sniffed type is `heic`, buffer the file (bounded by `MAX_FILE_BYTES`),
       call `heicBufferToJpeg`, and on `ok: false` return the upload-failed status. Store the JPEG;
       do not retain the original HEIC bytes.

    5. **Stage.** Generate `const token = crypto.randomUUID()` (Node built-in, no new dependency).
       Write to `buildPendingKey(token, fileUpload.name)` using a resumable upload, setting GCS custom
       object metadata `original_filename`, `content_type` (post-conversion), `original_content_type`
       (sniffed, pre-conversion) and `size_bytes`. That metadata is the single source of truth the
       promotion step in plan 04-17 reads — the client never supplies it again.

    6. **Respond.** `200 { token, contentType, sizeBytes }`. The response must NOT echo the filename,
       the object key, the bucket, or any signed URL. The client already holds the filename and
       interpolates it into the UI-SPEC error strings itself.

    Error mapping, all with generic bodies:
      `MaxFileSizeExceededError`  -> 413 `{ error: "File too large" }`
      `MaxTotalSizeExceededError` -> 413 `{ error: "Total upload size exceeded" }`
      more than `MAX_FILES` parts -> 413 `{ error: "Too many files" }`
      disallowed sniffed type     -> 415 `{ error: "Unsupported file type" }`
      HEIC conversion failure     -> 422 `{ error: "Could not process file" }`
      GCS or unexpected failure   -> 500 `{ error: "Could not upload file" }`
    Never echo `err.message`, never echo the filename, never include the object key. Each catch logs
    with an `[upload]` prefix carrying the token and byte count only — never `fileUpload.name`, and
    never the raw error object if it could carry request data.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated browser → upload endpoint | Nothing has been submitted yet, so there is no patient identity to authenticate against at upload time |
| multipart stream → server memory | An unbounded stream is a memory-exhaustion primitive on a 1 GB shared-CPU VM |
| patient bytes → GCS object | Once bytes land in storage, validating them is too late |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-4-58 | Denial of Service | Memory exhaustion via a huge or drip-fed multipart body | mitigate | `parseFormData`'s `maxFileSize` / `maxTotalSize` / `maxFiles` enforce during streaming, before full buffering. The route contains zero `request.formData()` calls, asserted by the verify script |
| T-4-59 | Denial of Service | Unauthenticated storage-cost abuse — no patient identity exists at upload time | accept with control | Caps plus one-file-per-request bound the per-call cost; CORS matches the existing submit route; staged objects self-delete under the `pending/` OLM rule (plan 04-17). Rate limiting is not built in this phase and is recorded as a Phase 8 hardening candidate |
| T-4-60 | Tampering | MIME/extension spoofing to smuggle a disallowed or executable file | mitigate | `sniffType` runs on the first `MIN_SNIFF_BYTES` before any GCS write; test case 5 asserts a spoofed `results.pdf` yields 415 AND that the storage write was never called |
| T-4-61 | Information Disclosure | Filename echoed in a response, an error, or a log line | mitigate | The 200 body is exactly `{ token, contentType, sizeBytes }`; every error body is a fixed generic string; test case 10 spies on both console methods and asserts zero filename occurrences |
| T-4-62 | Information Disclosure | Storage layout disclosed to the client | mitigate | The response carries an opaque UUID token only — no object key, no prefix, no bucket. The client cannot construct a storage path |
| T-4-63 | Tampering | Client-supplied file metadata trusted at promotion time | mitigate | `original_filename`, `content_type`, `original_content_type` and `size_bytes` are written to GCS custom object metadata by the SERVER at upload; plan 04-17 reads them from there, never from the client |
| T-4-64 | Information Disclosure | `@google-cloud/storage` telemetry to a non-BAA host (Assumption A3) | mitigate | Run a network capture during one upload and record every destination host in the SUMMARY. Any host outside `*.googleapis.com` is a stop-and-report condition, not a note |
| T-4-65 | Tampering | Malicious content inside an allowlisted type | accept | Ratified at plan 04-10 Task 2 item 6. Compensating controls: allowlist, size caps, `Content-Disposition: attachment`, no inline rendering. Revisit after the GCP cutover |
