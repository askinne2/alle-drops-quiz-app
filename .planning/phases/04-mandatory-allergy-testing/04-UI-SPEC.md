# Phase 4 — UI Design Contract: Mandatory Allergy Testing

> Visual and interaction contract for TEST-01…TEST-07. Generated by gsd-ui-researcher, to be
> verified by gsd-ui-checker. Every value below is grounded in `app/styles/quiz.module.css` as it
> exists today (1891 lines, unchanged design-system posture from Phase 3: no Tailwind, no shadcn,
> no component library, no design-token file). This phase is materially larger than Phase 3's
> contract because it resolves one genuinely open question the orchestrator flagged — the
> multi-file upload widget — and because D-09 restructures where the results screen sits in the
> flow, which has real visual and copy consequences beyond Part 7 itself.

requirement in `<decisions>` D-01…D-05. See Component Inventory §3 for the full argument.

this phase's content needs a 4th size or a 3rd weight, including the file-list rows, type chips,
and error copy — all fit within the existing Body/Caption roles.

### ⚠️ Required copy fix, not a style choice: "See results" is now false

Today's ternary (`QuizContainer.tsx:452-470`) shows **"See results"** on the last quiz part's Next
button. Under D-09's new flow (Part 7 → **consent** → submit → results), clicking that button no
longer shows results — it shows the consent screen. Leaving "See results" on that button would be
a live, patient-facing accuracy defect the day this phase ships, the same class of bug as DEF-04
(stale button copy that promises the wrong thing). **Fix required:** change the terminal-part
button label from `"See results"` to **`"Continue"`**. The button one part earlier still reads
`"Next →"`, unchanged.

### ⚠️ Deliberate, scoped deviation from Phase 3's "no inline error copy" precedent

Phase 3's UI-SPEC established: required-but-unanswered fields disable Next silently, with no
inline error copy anywhere in the quiz, and any fix should apply to all parts at once rather than
one-off. **This phase makes one narrow, explicit exception: `testing_files`.** Justification,
directly from the orchestrator's brief: D-02 makes this the single highest-abandonment point in
the entire flow (nothing persists until the terminal POST, so a stuck patient loses the whole
questionnaire), and the brief explicitly calls for "forgiving error copy" as a named mitigation.
Silence is the wrong choice specifically here, even though it is still the right choice for every
other required field in Parts 1–7. **Scope of the exception:** inline copy appears only for
`testing_files`'s own validation states (wrong type, too large, upload failed, and — the one truly
new case — "you haven't added a file yet" if Next is attempted with zero successfully-uploaded
files). `testing_year` / `testing_location` / `testing_allergens` keep the existing silent-disable
pattern, unchanged. Do not generalize this exception to the rest of the quiz without a real
decision to do so — Phase 3's deferred consistency item still stands.

## Flow Contract — the structural change D-09 forces (read before Component Inventory)

This is not purely visual, but every item in Component Inventory below depends on it, so it is
stated first. **The "outcome" screen, as a pre-consent step showing the patient's score, is
eliminated.** Today: `quiz_parts → outcome (score shown, action buttons) → [consent for some
paths] → submit → completed (thank-you)`. After this phase, every bracket takes one path:

```
quiz_parts (Part 7 last) → consent → submitting → RESULTS (terminal)
```

Score and bracket are still **computed** at the same point they are today (immediately on leaving
Part 7 — the existing `goToOutcome`-equivalent calculation is unchanged), but the computed values
are held in state and **not displayed** until after a successful submit. The screen the patient
sees immediately after Part 7 is **consent**, not results — which is what makes the "Continue"
button-label fix above load-bearing rather than cosmetic, and is exactly what closes the live
TEST-07 defect D-09 describes (a 0–2 patient today never sees `ConsentStep` at all).

**Consequence for `ResultsDisplay`:** it becomes the sole terminal screen, replacing today's
separate "completed" thank-you block (`QuizContainer.tsx:328-370`) rather than sitting alongside
it. The plain-anchor "Return Home" and "Go to AlleDrops Product Page" actions that exist in
today's "completed" block fold into `ResultsDisplay`'s action area (Component Inventory §5) —
this keeps them as plain anchors, not callback props, consistent with TEST-05's "terminal
component" requirement.

**Consequence for the consent step's Previous button:** its target changes from `setStep("outcome")`
(a step that no longer precedes it) to returning into `quiz_parts` at the last part index. This is
a behavioral requirement this contract states for completeness; the exact state-machine wiring is
plan/execution territory.

## Component Inventory — new / modified for Phase 4

### 1. The multi-file upload widget — position taken, with justification

**Position: `file_multi` is a new `QuestionType`, a normal `QuizQuestion` (`kind: "question"`) —
NOT a new `QuizItem` union member.** Its answer shape is `string[]`, exactly the array shape
`checkbox_multi`/`radio_multi` already use — an array of opaque upload-reference tokens returned
by whatever upload endpoint the backend plan introduces, not raw file blobs. This is the load-bearing
fact that makes the "fits the existing model" case work.

**Why this wins over a new `QuizItem` union member**, tested against the same standard Phase 2 D-09
used to justify info blocks needing their OWN union member (info blocks structurally *cannot* hold
an answer or be required — that is a real, compiler-enforceable distinction from a question).
`file_multi` has neither of those properties: it collects an answer, it is required, it composes
with `showIf` exactly like every other question. There is no invariant a new union member would
buy that the existing `QuizQuestion` shape does not already provide. Concretely, because the
answer is `string[]`:

- `required` / `isPartComplete` gating needs **zero new code** in `QuizPartRenderer.tsx` — the
  existing loop (`isPartComplete`, `QuizPartRenderer.tsx:359-366`) already calls
  `isAnswered(item, answers[item.id])` generically.
- `showIf` composition needs **zero new code** — `evaluateShowIf` never inspects `type`.
- `visibleAnswers`'s boundary-stripping (D-03) needs **zero new code** — a hidden `file_multi`
  question's tokens strip out at the payload boundary exactly like a hidden checkbox's values do,
  which is also the correct behavior for the orphan-cleanup edge case below.
- Scoring needs **zero new code** — Part 7 is structurally outside `ALL_SCORED_QUESTIONS` (same
  guarantee Phase 3 D-04 relies on), and `scoreQuestion`'s `default: return 0` covers it anyway.

**The one real code change this requires, stated precisely so the plan does not under- or
over-scope it:** `isAnswered` (`schema.ts:56-75`) is a switch on `question.type` with
`default: return false`. Three new type labels need to be merged into its **existing** behavioral
groups — this is a one-line diff per group, not a new function or a new operator:

```
case "checkbox_multi": case "radio_multi": case "file_multi":
  return Array.isArray(value) && value.length > 0;
case "text_input": case "text_input_short":
  return typeof value === "string" && value.trim().length > 0;
case "control_0_3": case "radio_single":
  return typeof value === "string" && value.length > 0;
```

That is the entire `schema.ts` blast radius. `QuizPartRenderer.tsx`'s switch statement gains one
new `case "file_multi":` branch (the widget below), exactly the same shape of change as every
prior question type. This is what "content plus wiring, no new mechanism" concretely means for
this field — the same standard Phase 3 held itself to.

**Two other new `QuestionType` values this phase also needs, same standard applied:**

- **`text_input_short`** for `testing_year` / `testing_location` — a single-line `<input
  type="text" className={styles.quizContainer__input}>`, not the 4-row `<textarea>` `text_input`
  renders. `.quizContainer__input` is already used this way today by `PatientInfoStep.tsx` for
  name/dob/email/phone — this is reuse of an existing class for a rendering shape the codebase
  already has, applied to a second question type. Using the existing `text_input` textarea for a
  4-digit year would be an oversized, mismatched control for the content it holds.
- **`radio_single`** for `testing_status` — a single required choice from custom-labeled options,
  rendered exactly like `control_0_3`'s existing JSX (`.questionCard__optionsVertical` /
  `.questionCard__optionVertical` / `.questionCard__optionSelected`, driven by `question.options`,
  true `<input type="radio">` elements). `control_0_3`'s literal type name ("medication control
  0–3") is misleading for a 2-option testing-status field with no numeric scale — this is the same
  granular-naming precedent the codebase already follows (`severity_0_3` / `frequency_0_4` /
  `bother_0_4` are separately named despite near-identical rendering, purely for downstream
  clarity — e.g. `app/lib/format.ts`'s label map, the PDF, the admin modal). **Zero-diff
  alternative, if the planner prefers not to add a type:** reuse `control_0_3` literally for
  `testing_status`, with a code comment disclaiming the name mismatch. Either is compliant with
  this contract; `radio_single` is the recommended choice for the reason above.

### 2. `.fileUpload` — new class family, every value composed from existing tokens

No existing class in `quiz.module.css` represents "a tappable card that triggers an action" (every
existing card is either passive — `.questionCard`, `.infoBlockCard` — or a pill/rect button —
`.quizNavigation__button`). This is a genuinely new visual role, which is why a new family is
justified under "reuse before invention" rather than forcing an ill-fitting existing class.

- **`.fileUpload`** — outer wrapper. Same base treatment as `.questionCard` (padding, background,
  radius) — it IS a question card, containing the label, the format/size caption, the dropzone,
  and the file list, in that order.
- **`.fileUpload__dropzone`** — the "Add files" tap target. `border: 2px dashed
  rgba(var(--color-foreground, 32, 34, 35), 0.15)` (dashed, not solid — the one deliberate visual
  departure from `.questionCard__option`'s solid border, signaling "drop/tap zone" rather than
  "selectable option," a distinction worth a one-property change, not a new pattern).
  `border-radius: var(--quiz-border-radius)`, `background-color: rgba(var(--color-foreground, 32,
  34, 35), 0.02)` (matches `.infoBlockCard`'s neutral fill), `min-height: 96px` mobile / `112px`
  desktop — **deliberately taller than the 44px floor**, because this is the single highest-stakes
  tap target in the entire application and must not read as equal-weight with an ordinary list
  option. Centered content: a `+` icon in accent color (`.fileUpload__dropzone__icon`, reusing the
  same inline-SVG technique as the info-block icon) plus the "Add files" label at the Label
  typography role. `:hover` and `:focus-within` both switch the border to solid accent
  (`rgb(var(--color-button, 0, 123, 255))`) with a `box-shadow: 0 0 0 3px
  rgba(var(--color-button, 0, 123, 255), 0.1)` — reusing the exact focus-ring treatment
  `.quizContainer__input:focus` already establishes elsewhere in this file, and reusing the
  `:has()`-based focus-visible technique this codebase already proved out
  (`quiz.module.css:1763`'s existing `:has(input[type="radio"]:focus-visible)` rule) so the ring
  appears correctly whether the patient tabs to the hidden native input or clicks/taps directly.
- **The `<input type="file" multiple>` itself** is visually hidden using the standard
  clip-based technique (`position: absolute; width: 1px; height: 1px; overflow: hidden;
  clip: rect(0,0,0,0); white-space: nowrap;`) — **never `display: none`**, which would remove it
  from the tab order and break the keyboard-reachability hard constraint. It sits inside the
  `<label>` that IS `.fileUpload__dropzone`, so native label-click-triggers-input behavior does
  the work, and `aria-label="Upload allergy test results"` plus `accept="application/pdf,
  image/jpeg, image/png, image/heic, image/heif"` are both set directly on the input.
- **`.fileUpload__requirements`** — the format/size caption, reusing the Caption role
  (`.questionCard__subtitle`'s exact typography), placed **above** the dropzone (see Interaction
  Contract — this is the "requirements stated before the picker" hard constraint made literal):
  "PDF, JPEG, PNG, or HEIC · up to {N} MB per file, {M} MB total."
- **`.fileUpload__list`** — wraps the added-file rows. `<ul role="list">` (role restated because
  `list-style: none` strips the implicit list role in some browsers), wrapped in a container with
  `aria-live="polite"` so add/remove is announced without a separate visually-hidden status node —
  the live region IS the visible list. `display: flex; flex-direction: column; gap:
  var(--quiz-spacing-xs);` mobile / `var(--quiz-spacing-sm)` desktop, matching
  `.questionCard__optionsVertical`'s existing gap rhythm exactly (this list of rows is structurally
  a sibling pattern to that one, not a new rhythm).
- **`.fileUpload__item`** — one row per file. Reuses `.questionCard__optionVertical`'s border /
  radius / padding / `min-height: 44px` treatment (a file-list row and an option row are
  structurally the same shape: icon-or-chip + text on the left, an action on the right) —
  **not** re-declared from scratch. Content, left to right: `.fileUpload__chip` (type badge, see
  below), `.fileUpload__filename` (Label role, `text-overflow: ellipsis; white-space: nowrap;
  overflow: hidden;` with `max-width` so a long camera-roll filename does not push the remove
  button off a 373px viewport), a status indicator (uploading spinner / success checkmark / error
  triangle — see Interaction Contract), and a remove `<button aria-label="Remove {filename}">×`,
  minimum 44×44px tap target, right-aligned.
- **`.fileUpload__chip`** — small neutral badge, `background-color: rgba(var(--color-foreground,
  32, 34, 35), 0.08)`, `color: rgba(var(--color-foreground, 32, 34, 35), 0.6)` (Secondary role,
  30% band, not accent — this is metadata, not a selection state), Caption size, text is the
  file's category: "PDF" / "JPG" / "PNG" / "HEIC".
- **`.fileUpload__error`** — the inline error line (see Copywriting Contract's deliberate
  deviation). `color: var(--quiz-color-error)`, Caption size, preceded by a `⚠` glyph (not a
  color-only signal), `role="alert"` so it is announced immediately and distinctly from the
  `aria-live="polite"` file-list region.

### 3. No thumbnail previews — uniform treatment for every file type, by design

**Recommendation: render every file the same way — type chip + filename + size — regardless of
whether it is a PDF, JPEG, PNG, or HEIC. No `<img>` preview for any type, not even JPEG/PNG.**

This directly resolves the hard constraint's open question ("HEIC has no browser preview... must
degrade to a filename + type chip") by making that the *only* treatment, not a fallback one type
gets while others get something richer. Reasons this is the right default, not a corner cut:

1. **Consistency.** A file list where JPEG/PNG show a thumbnail but PDF/HEIC show only a filename
   reads as broken for the ones without a thumbnail, even though nothing is actually wrong. A
   uniform treatment has no "why does this one look worse" question to answer.
2. **No new capability.** Rendering an `<img>` from a freshly-picked `File` needs a blob URL
   (`URL.createObjectURL`) and its own cleanup (`revokeObjectURL` on unmount/removal) — a small
   but real new behavior this phase does not need to introduce to satisfy any locked requirement.
3. **What actually reassures a patient photographing a paper panel is the filename**, which phone
   camera apps typically name descriptively or numerically in sequence (`IMG_4821.HEIC`), same
   information value with or without a thumbnail.

This is a recommendation, not a lock — if the planner has budget for JPEG/PNG thumbnails as a
later enhancement, nothing in this contract forbids it, but it is explicitly not required and the
uniform treatment is the one this contract signs off on for Phase 4.

### 4. Part 7 layout — standalone cards, deliberately NOT the HIST-03 gate/reveal fusion

Phase 3's `isGateItem`/`isRevealItem` fusion (`.questionCard__gateParent` /
`.questionCard__revealChild`) is keyed on a precise signature: `showIf` present **and**
`required === false`. Part 7's four `had_testing` children (`testing_year`, `testing_location`,
`testing_allergens`, `testing_files`) are all **required** — they do not match that signature, and
this contract recommends **not** touching it to make them match.

**Reasoning, stated explicitly so nobody "fixes" this as an oversight:** the visual fusion
technique signals "this optional field is a soft continuation of its yes/no gate — one thing you
might skip." That is semantically correct for HIST-03's three pairs and semantically **wrong**
here — Part 7's fields are not skippable once branched into, and the fusion pattern was designed
for a 2-card pair, not a 1-gate-to-4-children shape. Generalizing the shared detector to catch
required fields would also retroactively change Part 6's `has_pcp → pcp_clinic_name/address`
rendering (which currently does NOT get fusion treatment, and was already checker-approved as-is
in `03-UI-SPEC.md`) — an unnecessary, unrelated blast radius into an already-shipped, verified
screen. **Decision: `testing_status` and its four children render as standalone `.questionCard`s**
(each its own card, `.fileUpload` for the file question specifically), separated by the normal
`.questionCategory__questions` flex gap — the same uniform spacing every other multi-item part in
this quiz already uses. No new spacing token, no fusion classes applied here.

**No section heading for Part 7**, matching the established precedent Phase 3 confirmed (no part
in the flow carries a `.questionCategory__title`) — `testing_status`'s own question text carries
the topic, same reasoning Phase 3 used for HIST-01–04.

**Reveal appearance:** zero animation, same rule as Phase 3 §5 — the four children simply appear
at their natural flow position the instant `testing_status` resolves to `had_testing`, with no
fade/slide/height-transition wrapper. Nothing in this phase changes that standing rule.

## Interaction Contract Summary

| Behavior | Rule |
|----------|------|
| File picking is additive across invocations | Clicking "Add files" more than once must **append** newly picked files to the existing in-state list, not replace it — a native `<input type="file">`'s `onChange` FileList always contains only the latest selection, so the app must union it with prior state (dedup by name+size is a reasonable guard) |
| Required-gate satisfaction for `testing_files` | Only files that have finished a **successful** upload count toward "answered" (i.e., only their tokens are ever written into `answers.testing_files`) — a file still "uploading" or in an "error" state must not silently satisfy Next |
| File removal | Available at any state (uploading, uploaded, failed), immediate, no confirmation modal — not destructive per Copywriting Contract |
| No drag-and-drop requirement | Tap-to-pick via the native input is the required baseline interaction (consistent with the realistic mobile-photo scenario in the brief); drag-and-drop is an optional desktop enhancement, not required by this contract |
| No thumbnail previews | Uniform filename + type chip + size for every file type — see Component Inventory §3 |
| Hidden-answer retention applies to files too | If a patient flips `testing_status` from `had_testing` back to `needs_testing` (and back again), already-picked/uploaded file tokens in React state are **not** cleared — same D-03 rule Phase 3 already established for typed text. `visibleAnswers` strips them at the payload boundary only if the field ends up hidden at submit time |
| ⚠️ Orphaned-upload flag for the planner | The rule above means a file uploaded while `had_testing` was selected, then hidden by flipping to `needs_testing` before submit, never reaches the backend as a linked token — the uploaded blob becomes orphaned storage. This is a direct interaction-design consequence worth flagging explicitly; the retention/cleanup policy itself is Claude's Discretion per CONTEXT.md D-04, not resolved here |
| Exclusive option handling | Not applicable to Part 7 — `testing_status` is single-select by construction (`radio_single`/native radios), not a checkbox list with an exclusive flag; the D-13 reversal's "never disable a sibling" rule is inherited automatically because true radio inputs never disable siblings in the first place |
| Keyboard reachability | The file `<input>` sits inside its `<label>` using the visually-hidden (not `display:none`) technique, so Tab reaches it and Enter/Space triggers the native picker; the dropzone shows a visible focus ring via `:has()` exactly as `quiz.module.css:1763` already does for a radio input |
| Screen-reader labeling | Input: `aria-label="Upload allergy test results"`. File-list container: `aria-live="polite"` (add/remove announced). Error line: `role="alert"` (announced immediately, distinct from the polite list region) |
| Per-file status icon has a text equivalent | The row-level status indicator (spinner / checkmark / error triangle) is `aria-hidden="true"` and carries a visually-hidden text sibling — **"Uploading"**, **"Uploaded"**, or **"Upload failed"** — so the icon is never the sole carrier of per-file state. Without this, a screen-reader user hears the filename announced by the `aria-live` region but not whether that file actually succeeded, which is exactly the state the required-gate depends on |
| Error signaling is never color-only | Every error state pairs `var(--quiz-color-error)` text with a `⚠` glyph prefix — never color alone, satisfying the accessibility hard constraint directly |
| Consent step Previous target | Changes from `setStep("outcome")` to re-entering `quiz_parts` at the last part index — see Flow Contract |
| Part 7 terminal button copy | `"Continue"`, not `"See results"` — see Copywriting Contract's required fix |
