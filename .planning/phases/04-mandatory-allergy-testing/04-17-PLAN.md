<objective>
⛔ **BLOCKED** — see `blocked_on`. Do not start until plan 04-10's checkpoint clears.

Close the loop between staged uploads and persisted submissions, and make the orphan-cleanup rule
safe.

At the terminal POST, `answers.testing_files` holds opaque tokens pointing at objects under
`pending/`. Promotion copies each to `submissions/{id}/`, inserts a `submission_files` row, and
deletes the staged copy. GCS has no atomic rename, so this is copy-then-delete with N+1 points of
partial failure (04-RESEARCH.md Pitfall 3). The plan must decide, not paper over, what the patient
sees when the submission succeeds and promotion does not.

The lifecycle rule is the other half. An age-based delete scoped to `pending/` is the orphan cleanup;
the same rule applied bucket-wide would eventually delete promoted, retained clinical files, directly
violating the 6-year HIPAA retention constraint and the standing rule that submission data is never
deleted during incident response.

Purpose: TEST-04's persistence linkage plus its retention posture.
Output: a promotion step, a prefix-scoped lifecycle rule proven against real objects, a retention
document, and a VM sized for the new work.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client-supplied token → storage path | A token is interpolated into an object key and must be validated first |
| staged object → permanent retained object | Promotion is copy-then-delete across two systems with no shared transaction |
| lifecycle automation → retained clinical files | An automated delete rule is the only mechanism in this system that can destroy PHI |
